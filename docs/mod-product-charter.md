# CoopCraft 全模组产品纲领与复杂度预算 v1.0

> **适用范围：整个 CoopCraft，不只文明演化。**  
> 状态：拟议设计规范，供 PR 审查后采纳，不表示已修改游戏行为。  
> 制定：2026-11-05；核查基线：`main@17296af707a08a334a94c4cb75b59472ec2dca5b`，Minecraft 1.21.1 / Fabric；构建与测试规范以最新 `AGENTS.md` 为准。  
> 文档关系：现有 [文明设计](civilization-design.md) 是当前功能与工程状态记录；此文档旨在约束**未来功能的产品范围与验收**。研究文库 [PR #24](https://github.com/ThySummer14/coopcraft/pull/24) 提供论证和备选机制，不自动等于代码需求。

## 0. 一句话目标与非目标

**产品目标**：朋友在 Minecraft 中正常探索、生产、建造、联机；世界里有真实行动与历史的居民，让玩家可以观察、参与并影响其变化，却无需成为全职管理者。

**刻意不做**：
- 不把 CoopCraft 做成需要每天操作几十个面板的战略管理游戏。
- 不把“研究中的一个历史现象”默认转化为一套可见 UI、数据对象和独立 AI。
- 不把完整社会史、所有生产资料制度与复杂政治经济模型作为一个发布版的完成条件。
- 不以固定 `S0→S1→…` 科技等级驱动所有产权、家庭与制度自动变化。
- 不为“更真实”牺牲原版 Minecraft 生存、多人体验、存档或服务器性能。

## 1. 两条平等的产品主线，互不绑架

| 主线 | 现有具体功能 | 体验定位 | 技术边界 |
|---|---|---|---|
| **Co-op Quality-of-Life**（轻联机） | 全队进度toast、坐标/死亡点共享、路径点、队友血量等；`README.md`为功能事实来源 | 即装即用、低频干扰、可靠 | 不要求建立聚落；无文明NPC时仍独立工作；服务端验证，避免消息洪水 |
| **Living Settlements**（活的文明） | 钟创建聚落、NPC工作、真实采集/加工、公仓、人物、施工、可选社会模拟 | 环境叙事、玩家可影响的自治社会 | 聚落是主动接触入口；无需玩家持续下令；限制规模与真实世界边界 |

此外，**自动农艺机、整合包附带的第三方模组**应按独立功能/分发资产管理，不是文明必须拥有的前置条件。整合包中的 DangoMusic 属于单独加载的第三方组件，不应混入文明演化的服务端模拟逻辑或相同发布义务。所有第三方资源继续依 `modpack/README.md` 登记来源、许可证、校验及源码要求。

**默认行为**：轻联机功能不因世界有没有聚落而失效；文明新增功能只对加入、登记或明确启用的世界/聚落施加影响，具体开关应尽量复用现有约定，不为每个功能造一页设置。

## 2. 五条强制设计决策（ADR-MOD-001..005）

### ADR-MOD-001：三层复杂度隔离

1. **玩家层：简单**。原则上右键居民/现场方块、原版物品、钟/既有名册即可进入；日常强制管理任务=0。
2. **运行层：少而可靠**。优先复用居民基本需求与任务、真实物品/仓库、少量关系与规范、事件记录四类能力。已实现的纯Java模拟复杂模块可以保留为实验台，但不自动接入世界中的每一种微观行为。
3. **研究层：允许复杂**。跨时代研究文库用来检验历史概念、生成可比较方案、给未来拓展提供边界，但**研究深度不是实现承诺**。

### ADR-MOD-002：一个阶段只做一个有辨识度的**签名玩法**

| 研究单元（不是必经进化阶梯） | 玩家主要可见的新循环 | 共用已有机制；不要每阶段重新做 |
|---|---|---|
| S0 混合采集/早期共同体 | **探索/劳动 → 真实食物 → 分享/互助 → NPC回应** | 基础需求、职业倾向、事件、仓库 |
| S1 定居农作 | **播种/等待/收获 → 吃或留种 → 下一轮生产** | 真实方块、物资保管、基本任务 |
| S2 早期组织/国家形成 | **公共建设/征集/拒绝 → 工程进展与关系后果** | 集体工程、实际材料和任务 |
| S3 领主/租佃安排 | **使用耕地 → 按约定交租或履行劳役 → 剩余变化** | S1田地、收获、承诺和真实转移 |
| S4 商业城镇 | **带货/开店/交换 → 实际成交 → 货物流转** | 单一库存与运输 |
| S5 资本主义生产 | **采购投入 → 雇佣与生产 → 销售/工资/利润** | 商店、合同与实际工作，利润与价值分析保持区分 |
| S6 合作/公共组织 | **共同决定生产安排 → 投入工作 → 收益分配** | 任务、经营、基本决策 |
| S7 假说性未来形态 | 仅形成研究备选，验证基础玩法后再决定特色 | 不预置庞大科技树 |

**限制**：上述是帮助发布可玩切片的研究标签，不是每个世界的阶段属性；同一世界可以有不同生产方式并存，能逆转。

### ADR-MOD-003：行动结果优先，历史名词延后

是否新增一个核心系统，需满足以下至少四个可审查条件：
- 玩家能在普通游戏中观察到具体差异（物品、位置、建筑、行动或对话原因）；
- 玩家可以有意义地参与或选择不参与；
- 没有玩家时 NPC/联机功能仍自主运行；
- 可复用现有系统，而非重造第二份任务/货币/库存/权利账本；
- 可用确定性的GameTest/场景卡证明因果和无副作用。

未满足：研究保留 `research/` 或 Issue 的 Backlog，不进入 P0/P1代码实施。

### ADR-MOD-004：仅当有独立玩法时才公开新参数/菜单

- **默认信息**：居民当前在做什么、为什么失败、玩家能怎样帮。无需展示“社会制度因子、二十个属性和统计公式”。
- **第一入口**：右键居民，最多数条常用情境行动；方块和物品优先复用原版互动；钟或名册用于“只读概况/事件历史”。
- **重要事件**：可自然出现少量反馈；可忽略、不刷屏、不要求立即决策。人格、关系等高级信息默认收起或只在开发探针可见。
- 任何 UI 必须检查原版窗口、HUD、键位、中文与英文文本的基本可读性和可退出性。现有 `README` 将共享路径点列表设为默认 `M`，同仓库整合包 DangoMusic 也描述 `M` 为播放器快捷键，**须实际装包测试是否有冲突并提供改键/冲突指引**；不可仅凭 README 宣称已重现运行冲突。

### ADR-MOD-005：性能、多人和兼容是新功能的入场券

- 服务端永远是资源、劳动产出、实体动作、权限与共用设置的权威；客户端请求必须检查距离、权限、库存、频率与当前状态，不能信任来自客户端的“完成任务/凭空增加物品”。
- 与现有 `Civilization.tick` 和 `VillagerWorkGoal` 的调度共存，避免将每个居民的每个社会推理都放进每个服务器 tick。**事件驱动或有限时间片规划，实体动作按原版AI节奏执行**。
- 不在每tick全聚落扫描/全图搜索/无限路径重算；只在已加载且登记的实体附近作增量检查，使用失效缓存与实体负载预算。
- 对有无聚落、活跃/不活跃聚落、不同人数设可比测试。未加载区块不因为“模拟日过去”就免费生成方块、实体或完成搬运。
- 单人/双人联机按**真实客户端FPS与帧时间、服务端MSPT与慢tick、网络延迟/抖动/丢包**分别定位；不要仅由RAM充足、TPS正常或Tailscale显示直连判断不卡，也不要无证据推荐VPS。
- **性能提议验收线（需实测校准）**：同种子同视距、2名玩家、16名已加载登记居民，开启功能相对关闭功能的服务端p95 MSPT额外开销目标不超过2ms，且无持久>50ms慢tick；关键交互无明显连续丢帧、服务端不向客户端每tick发送完整聚落数据。**这些是初版工程目标，不是已测试达标或历史承诺**。对比基准必须留记录。
- Debug profiling 使用仓库已有 dev-only `tools/probe`，可选 spark（明确为诊断工具，不属于运行必须依赖）；正式发行 jar 不打包探针或客户敏感配置。
- 原版村民农耕、繁殖、原版手部动作及其他模组兼容必须测试；只接管确实登记并明确受Mod管理的操作，不全服覆盖所有村民AI。
- 旧 `SettlementSavedData` 中已有UUID/道具/社会事件及版本信息，新字段采用向后兼容缺省并验证至少两次重载，不能靠重新建世界通过测试。

## 3. 现实中的实现层：避免“每项历史研究新增四个Java类”

| 运行基础能力 | 是否已有实物/原型 | 未来新增功能的首选扩展方式 |
|---|---|---|
| 居民身份、基础需求与任务 | 已有 UUID、人格、饱食、`LaborAllocator`、`VillagerWorkGoal` | 扩展现有工作选择、失败原因；首版不要平行“家庭AI/政治AI/农业AI” |
| 单一真实物资与世界变化 | 已有公仓、`MinecraftStockpileAdapter`、生产事件与施工 | 加具体物品映射/收获动作，再考虑新的产权和货币 |
| 一层简化的社会关系 | 已有信任、帮助记忆、规则与实验核心 | 首版用有来源的重要事件影响行动，不要求全部亲缘/照料/财产图谱上线 |
| 聚落条件与可见历史 | 已有名册、建造进度、事件页、阶段显示 | 展示当前真实事实和原因；不要新增十个报表面板 |
| Co-op 网络和路径点 | 已有 `CoopNetworking`、服务器世界存档 | 保持客户端/服务端职责清楚、校验频率和同服一致性 |

**架构边界**：纯Java `civilization.simulation` 继续是可复现研究实验台；真实 `ServerLevel` 的作物/方块、原版容器、已加载NPC行动不能被纯Java另做一份“已完成”。如果需要桥接，先定义谁拥有该动作最终结算权和一条幂等事件，再开始写代码。

## 4. 玩家不会玩累的具体检查

**15分钟评测（测试情境，不是固定故事）**：
1. 玩家正常进入已有聚落：能见到NPC行动，且无需打开面板；
2. 右键一人，知道其当前活动和一个真实阻碍；
3. 玩家用现有Minecraft操作实际帮助一次：交食物、采集材料、参与建设或未来的耕作；
4. NPC依自己的规则作出可观察回应，可能接受也可能拒绝；前提变化可改变后续任务；
5. 玩家离开继续原版生存；不用每日打卡，也不会受到“忘管村庄”的无理处罚。

**可玩失败**：玩家帮了却无反馈；所有村民被卡在站立/排队；每1分钟弹出求助；看不到普通Minecraft行动和聚落的关系；整套系统只能通过打开名册操作；必须先读长文献才能理解“阶段为什么升了”。

## 5. 从旧文档/研究到开发任务的降级规则

| 原设计项 | 处理方式 | 何时升级到正式开发 |
|---|---|---|
| S0食物、简单帮助、居民工作、现实公仓/建造 | **保留核心且先修稳定性** | 作为跨阶段真实行为底座 |
| S0复杂的照料时段、四重关系网、详细规范传播 | **简化/研究保留** | 当真正的可见场景需要时，仅接必要动作 |
| S0长期迁徙/所有远方营地细节 | **实验/延期** | 实际玩家探索能引出可见的线路、搬运和留居选择 |
| S1马铃薯真实农田、粮食留种 | **一个完整小切片** | 前一项数据/劳动来源GameTest通过 |
| S1土地完整权利束、永久地权、家庭实物仓、复杂改良 | **先只读研究，延期实装** | 有可复现玩家冲突场景证明只用“当前使用者”不够 |
| S2–S6征集/地租/交易/雇佣/合作 | **每单元一条可玩循环** | 先复用前期真实生产和库存，不同时开五条代码主线 |
| 全局宗教、外交、阶级模拟、精细市场、LLM常驻NPC、超大科技树 | **远期备选** | 有明确可玩验证、可控成本、性能/存档验收，才转Issue |

同一 Issue/PR 若超过一个可独立验证的循环，必须拆分。**拒绝“按研究文档把所有类名完整实现”这种开发指令**。研究文本中的`record`和状态机主要是分析工具，未经过必要性审查不能成为必做接口。

## 6. 协作开发与 PR 入场标准

**每个功能PR必须回答六件事**：
1. 玩家看见/能做什么？一句话描述，最好附真实游戏截图或测试卡；
2. 使用哪一项旧系统？新增哪些文件与持久化字段？有没有平行库存/模拟？
3. 有什么动作与哪个`BlockState`/`ItemStack`/`Event`直接相连？
4. 单人、两人、无玩家、卸载/加载/两次重载，分别会怎样？
5. 哪些指标能表明它没拖慢客户端/服务端或刷屏？给基线与测量；
6. 什么不做？指出被故意延后的历史模型与UI。

**合并门槛**：遵守 `AGENTS.md` 的 `./gradlew build runGameTest`、Fabric环境、资源/许可核查、中文/英文文本、兼容性与回滚路径；对测试Flaky必须说明，不能称“构建通过”而未跑。先合并影响最小的1条行为，再加复杂规则。功能有明显缺陷时先fix而非继续叠新时代。

## 7. 研究文库与此文档发生冲突怎么办？

**优先级**：
1. 真实运行源码、原版Minecraft行为和实测（当前到底做了什么）；
2. `AGENTS.md` / CI / 旧存档兼容（安全与工程约束）；
3. **本纲领与后续维护者明确批准的发布范围**（做不做、先后顺序）；
4. `docs/civilization-design.md` 中与当前代码核实一致的设计；
5. `research/` 跨时代研究（为何这样设计、未来可选机制）。

这里的“优先级”针对功能范围和事实判定，不代表研究被删除、否定或不允许历史事实纠错。若`AGENTS.md`和实际CI冲突，需要以可验证的构建结果反馈更新规范。

**不在本PR修改运行中的`SettlementStage`单向枚举、人物人格或经济算法**。它们是已知需要评审的具体工程问题，不应借“产品瘦身”做大规模重构。

## 8. 本次提案的成功条件

- 开发Agent可以用本文拒绝不必要的功能范围，而不是把全部研究当TODO。
- 阅读主README的人知道“轻联机与文明”是两个都重要且独立可用的方向。
- 下一批工作能落在少数优先的单循环、兼容与性能问题上，避免一口气新增完整政治/农业/家谱体系。
- 游戏玩家不因加入CoopCraft就必须读复杂经济学或每天操作行政菜单。
- 这些是**审查通过后采用的项目管理原则**；本PR只提交文档与导航，没有宣称代码行为改变。
