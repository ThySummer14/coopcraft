# 真实营火烹饪：待实现的许可、归属与消费

这是第九十五增量期间核查的设计缺口，不是已上线的自动烹饪功能。已有营火建造、登记和聚落里程碑也不等于居民已经会烤食物。

## 现状与不能直接复用的边界

- `Civilization.onUseHearth` 允许玩家登记炉火，但 `SettlementStages.initialize` 同样会把扫描到的普通或灵魂营火写入 `setHearth`。当前 `SettlementSavedData` 只存位置，不保留登记来源或操作许可。旧炉火位置、自动观察、同种方块都不能证明可以占用槽位或取走玩家食物。
- `SettlementFood` 的实物饱食适配沿用原版村民食物点并补充甜浆果，目前没有烤马铃薯。给背包放熟食并不能自动使既有个人进食、口粮或分享流程识别它。应扩展聚落实物食物适配器并逐个核查消费路径，不能为了这一功能改动原版繁殖食物表。
- 带年龄食物以及格式异常的年龄标记继续被 `RecipeManagerFoodAgeMixin` 拦在普通及缓存配方之外。不能去标记、重设新鲜度，或把带年龄的公共原料当作普通私人食物烹饪。
- [Minecraft 1.21.1 Mojang 映射接口](https://mappings.dev/1.21.1/net/minecraft/world/level/block/entity/CampfireBlockEntity.html) 显示 `CampfireBlockEntity` 不是 `Container`，有 `getItems`、`getCookableRecipe`、`placeFood`、`cookTick`、`cooldownTick`、`dowse` 等接口，烹饪时间是内部数组。接口没有提供本模组的槽位拥有者或熟食保管凭据。此次没有核实目标版本方法体、精确掉落/拆分/保存顺序和安全注入点；实现前必须补核，不能套用别的版本。

## 建议的最小闭环

1. 独立明确授权一个普通营火用于聚落烹饪，支持查询、撤销，保护区优先。授权固定营地、维度、位置及代次；撤销后同位置重授也使旧票失效。旧档默认无授权，已有 `hearth` 和新自动扫描不授予许可。第一步若仅完成许可管理，必须明确尚无自动烹饪。
2. 首批只考虑默认实物模式成人的1颗本人普通马铃薯，不接公仓或抽象库存，不占用玩家已有原料的槽位。规划只读，实际到安全操作位置再投入一个真实输入；调用接口的扣料行为须核实，不能既手动扣一次又让接口扣一次。
3. 在真实槽位变化和产品产生处建立可验证的批次关联。投入或等待不等于完成，槽位空了也可能是玩家取走、方块被拆或其他行为。不能凭附近掉落物的物品类型和坐标认领熟食。
4. 真正取得这一份实际熟食后，才由个人进食流程消费并恢复饱食。烹饪完成、取回、吃下是三个不同事实，经验、产品事件和社会记录只能跟随各自证据。

## 产品归属仍须先选定并验证

**沿用原版掉落：** 必须在产品创建点确认本批身份，再跟踪实际掉落实体与数量。要处理合并、拆分、玩家/漏斗先拿、销毁和重载；不能假设实体目标字段就是独占保护。近旁的其他熟食始终不是本批的替代品。

**保留在自定义输出位置：** 会改变原版营火完成后的行为，需明确告知并完整设计真实输出存储、玩家交互、方块拆除和保存重载。不能一边保留世界掉落，一边向背包生成副本，也不能仅取消掉落却没有可恢复的实物保管位置。

在其中一种方案有完整证据之前，不实现“等待若干tick后往背包发熟食”的捷径。

## 中断、旧档与守恒

- 满包、灭火、破坏营火、撤销许可、新增保护、成员/模式变化、死亡、卸载、重载都会使工作资格失效，但不能因此补发输入或产品。
- 已投入的真实物品留在其实际保管位置。临时票不保存物品副本；恢复需要可持久验证的槽位/批次关系，否则保守停止新领取，保留原版物品行为。
- 旧档和未知槽位不自动认领，不删除玩家食物，不通过猜测恢复归属；同类营火被替换且期间没有可观察证据的边界必须明确。
- 操作位置需避免火焰伤害，所有读取及移动仍受已加载活动区块、世界边界和保护限制。没有开展世界实机验证，不能承诺寻路或原版AI竞争已通过。

## 实现前应具备的回归

- 自动发现/旧档无许可、显式授予/撤销、同位置重授失效、保护覆盖及任务中途变更。
- 普通原料与命名/年龄/异常/其他用途物隔离；完整扣一份、失败不重复扣或补发。
- 只有真实完成证据可生成完成记录；空槽、计时到期、玩家槽位和附近其他产品不能冒认。
- 熟食被他人先取、掉落合并/拆分/销毁、满包、灭火、拆除、死亡、正常保存重载。
- 获得熟食不直接恢复饱食；一次实际消费仅扣一份，其他口粮、分享与公共库存适配不发生重复计量。
