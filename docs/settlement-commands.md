# 聚落命令与统一实测流程

命令只选择**玩家所在维度、距离玩家64格内最近的已登记聚落中心**；等距按聚落ID稳定选择。没有目标时明确报错，不创建聚落。控制台无玩家身份不能执行。`/execute` 改写位置或维度也不会替代实际玩家位置与维度。

## 命令

| 命令 | 权限 | 作用 |
| --- | --- | --- |
| `/coop settlement status` | 普通玩家 | 查看开关、登记床位与缺口、真实/抽象公仓库存、施工和待建项目 |
| `/coop settlement observations` | 普通玩家 | 只读查看居民曾观察到的甜浆果候选、位置与未知来源；不授予采收权 |
| `/coop settlement observations suppress <ID>` | OP等级2 | 持久抑制已有观察记录，重扫不恢复；不控制旧浆果采收 |
| `/coop settlement observations resume <ID>` | OP等级2 | 显式移除抑制并释放记录，之后须重新观察 |
| `/coop settlement materials` | 普通玩家 | 同上，重点用于核对项目剩余消耗与缺口 |
| `/coop settlement reserves` | 普通玩家 | 只读查看当前备粮目标、权威库存、目标量与差额 |
| `/coop settlement reserves normal\|high` | OP等级2 | 选择常规或加倍备粮目标，仅影响觅食者后续补储备判断 |
| `/coop settlement meeting` | 普通玩家 | 只读查看今日会议机会、选中议题与当前规则效果 |
| `/coop settlement meeting hold` | 普通玩家 | 在真实公仓旁组织已有议题的一次现场讨论；不是玩家投票 |
| `/coop settlement meeting autonomy` | 普通玩家 | 只读查看仓旁自主协商设置，旧档默认关闭 |
| `/coop settlement meeting autonomy on\|off` | OP2 | 单独开启/关闭仓旁自主协商，开启前需已有survival+norms |
| `/coop settlement rations` | 普通玩家 | 只读查看已加载居民当日件数额度、所领食物含营养与当前饥饿 |
| `/coop settlement construction` | 普通玩家 | 只读查看任务蓝图ID、原点、nextIndex、保存/当前指纹与兼容原因 |
| `/coop settlement construction adopt <fingerprint>` | OP等级2 | 显式核验并为无签名旧任务补签名 |
| `/coop settlement events [count]` | 普通玩家 | 查看最近事件、ID、直接原因与详情；默认5条，可指定1–12条 |
| `/coop settlement simulation <开关> <true或false>` | OP等级2 | 通过现有服务修改开关 |
| `/coop settlement import <资源> <数量>` | OP等级2 | 从已登记公仓真实物品显式转入抽象库存 |
| `/coop settlement export <资源> <数量>` | OP等级2 | 从抽象批次显式转回已登记公仓 |

开关固定为 `survival`、`production`、`skills`、`growth`、`norms`，均有补全。后四项开启前必须先开 `survival`。关闭 `survival` 同时关闭其余四项，但**保留抽象库存**。观察命令不会创建模拟状态或开关，也不会导入/导出物品。

数量必须为整数 **1–4096**。资源使用下列小写名字，支持Tab补全；不接受任意物品ID。

| 资源 | 对应真实物品 |
| --- | --- |
| `wild_fruit` | 甜浆果 |
| `tubers` | 马铃薯 |
| `fish` | 生鳕鱼 |
| `game` | 生牛肉 |
| `wood` | 橡木原木 |
| `stone` | 圆石 |
| `stick` | 木棍 |
| `smooth_stone` | 平滑石 |

仅普通、没有自定义组件修改的对应物品可导入。例如烤马铃薯、熟鳕鱼、其他树种原木不在映射中。`fish` 是资源名，不能写成 `cod`。

## 可复制的游戏内流程

1. 在附近32格内至少有两名服务器当前可用维度中均未登记归属的存活村民处放置钟，正常右键钟，登记聚落及已加载居民。已有其他聚落归属的访客不计作新创始者。不要潜行点钟。
2. 在聚落中心48格内放箱子或木桶，潜行右键登记公仓。放入普通马铃薯64个，以及准备测试的原木、圆石等。确保仓库及相邻区块已加载，箱子没有被遮挡。
3. 站在聚落中心64格内，以OP等级2玩家依次执行：

```text
/coop settlement status
/coop settlement simulation survival true
/coop settlement simulation production true
/coop settlement simulation skills true
/coop settlement simulation norms true
/coop settlement import tubers 64
/coop settlement materials
/coop settlement rations
/coop settlement events 5
```

**开启survival后真实公仓食物不会自动导入。未显式import就可能缺粮。** 此模式暂停模组定时公仓维护中的真实食物上缴/基础口粮配发，避免把待导入粮食搬到无法参与模拟进食的居民背包；该维护不再搬运原有背包食物，材料则走实际返仓。关闭survival后恢复实体基础口粮配发；浆果/土豆超额库存按下文实际返仓，其他食物仍沿旧上缴策略。survival模式保留采集后的既有浆果上缴，也不阻止原版村民或其他模组自行搬运/消耗食物。模拟模式不再借这条定时维护自动补充原版繁殖用的背包口粮；抽象饱食不等于满足原版繁殖条件。 请紧接着导入食物，并根据居民数持续观察补粮。若仓库没有足够马铃薯，返回实际交接数会小于64；不能把请求数当成实际库存。也可放入生鳕鱼并执行 `/coop settlement import fish 32`。

4. 可选：`/coop settlement simulation growth true` 开启已有的成长映射；它本身不保证立刻出生或自动繁殖。
5. 测试材料往返：公仓放入圆石后依次执行：

```text
/coop settlement import stone 16
/coop settlement materials
/coop settlement export stone 5
/coop settlement materials
```

预期导入时真实库存下降、抽象库存等量增加；导出反之，不凭空生成。导出依模拟仓库批次顺序（到期日优先，其次批次ID），不混用其他资源。满仓可能只导出一部分或0个，反馈必须与实际移动数一致。

6. 执行 `/coop settlement simulation survival false`，检查五个开关均为false，抽象库存仍在。需要时用export取回；关闭模拟不阻止显式交接。
7. 用普通玩家验证status/materials仍可读，而simulation/import/export不能使用。离开所有聚落中心64格后，再执行status，应提示无聚落而不创建新聚落。

## 配给观察：件数与营养分开

`/coop settlement rations` 只在模拟生存开启时显示配给台账，不创建状态或开启功能。范围为当前聚落中已映射、真实已加载、仍存活且距中心64格内的成员；按UUID稳定排序，最多显示32行，并说明省略人数。查询不强制加载居民、不发放食物、不重置额度或推进核心日。

每行给出核心日、已领件数/每日额度/剩余件数、所领食物含模拟营养、当前饥饿（越高越饿）。营养从当天实际公仓分配事件的历史营养值汇总，件数以持久化配额台账为准；二者不匹配、历史不完整或超出数值范围时显示未知，不补造数据。

**食物所含营养不等于实际缓解的饥饿量，也不是现实热量。** 例如恰好领到3份野果含54模拟营养，3份猎物含84；实际进食仍会按当前需要停止，不保证每次吃满3份。此命令不改变既有件数规则，不加入营养额度、紧急补领或新分配制度。

跨日后若尚未首次领取，旧日台账仍可保存在文件中，但不计入今天额度。保存重进应保持这一点；同日重进不能重置已领件数。缺日期历史不会被查询或加载器伪造成今天的记录。

名册的真实额度拒绝事件会保存并显示当时的已领件数/上限、饥饿、需要营养和公仓可用营养。公仓有粮而拒绝，可能是件数额度已经耗尽；公仓为0时也不隐藏事实。它只解释已经真实发生的拒绝，不触发额外领取或改变政策；旧事件没有保存的依据不会根据今天的库存倒推。

## 可复制的事件证据

`/coop settlement events` 默认取最近5条；可指定1–12条，按时间先后显示选中的尾部。每条包含稳定事件ID、核心日、类型、资源与数量，以及最多4个直接原因ID（更多时提示余量）和名册已有详情。它不是递归展开完整历史的命令，资源列沿用事件投影的第一种资源与数量汇总，不代替多资源交易明细。

即使已关闭survival，历史仍可查看。空聚落/没有模拟只提示无事件，不创建状态；重复查询不产生交易、社会结算或新事件，不导入/导出物品、不主动加载区块。人物名只读取已加载实体或使用现有确定性名字，名册中的提案详情仍沿用已有投影语义。

新制作完成记录会显示产物及数量、直接证据范围和“原有真实库存来源未知”。原因ID只证明本次同步制作期间的直接导出；不能把少量原因或空原因理解为已追溯全部原料。旧记录没有这些字段时不按当前配方补造历史信息。

遇到配额拒绝或规范问题时，可同时保存status、rations与events输出，并记下模组提交版本；事件ID有助于对照请求、分配、拒绝与监督的直接来源。拒绝的全部六项依据可在聊天记录中查看，不受名册面板高度截断。

## 床位登记与失效验证

- 床脚在聚落中心48格内时，**主手空手、潜行右键完整床**可显式登记公共床位。床头或床尾均可点击，均以床脚选择聚落，所有床颜色均支持。同一床重复登记不增加容量，已属于其他聚落的床不能重复登记。
- 这只是登记既有床，不生成床、不搬动物品、不强制分配睡眠位置；新的低频维护只检查已登记床，不会额外扫描附近床。既有的右键钟初始化调查仍会登记32格范围内发现的完整床和设施；本轮保留该兼容行为。
- 拆掉已登记床后，保持相关区块加载，等待至多100 tick（正常20 TPS时约5秒），再查询status：登记容量应下降，住房缺口和建材需求恢复。
- 床的另一半或相关区块未加载时保留旧记录，不读取未知方块或强制加载。重新加载后再核验。
- 补足完整床并重新显式登记，住房缺口应关闭。已开工项目仍按既有规则完成，不撤销已经消耗的材料。
- 当前缺床会在空地另行补建，不是原地修理旧房；登记容量不代表床已被占用、寻路可达或满足原版繁殖条件。

## 施工进度与暂停

status和materials会同时显示保存的施工步骤数、蓝图ID、下一位置与当前原因。命令只读，不会挑选新项目、推进步骤或交接材料。

- 下一格已有任何非空气方块时暂停，包括玩家放入的相同方块；不拆除、不退款、不丢弃原项目。玩家清障后沿原址续建。
- 门/床两步另核验配对格：付费首半要求下一半仍为空，免费续半要求已放首半与蓝图完整状态一致。配对格未知、被占或首半被拆/改时暂停；开关门、供电等属性变化也可能触发。不会自动恢复、重复扣费或接受玩家补建的完整一对，见文末配对验收。
- 缺料、仓库不可用、目标未加载或不处于实体tick区域时等待，不凭空完成。材料只在抽象库存而公仓满/槽位拒收时，显示“公仓无法接收下一步材料”；已有真实材料或无需耗材的续半块不因满仓误停。
- 活体占位会显示实体阻挡，既有施工居民退让仍保留；检查结果不等于取得施工锁，多名居民实际动手时还会再次核验。
- 最后一步涉及住房完工时，所有计划床的登记位置都必须能按现有加载规则核验。任一床返回未加载则暂缓最后一步，不落块、不扣料、不清除工程；加载恢复后重新判断。已加载但损坏的床不阻止完工，也不会被算入床位。
- 蓝图暂时缺失、存档步骤越界会显示不可用并保留任务，不自动清空进度或登记完工。恢复原始蓝图后可重试。新任务绑定稳定版本指纹，蓝图变更会暂停；无签名旧任务需显式核验补签名，不自动迁移。
- 查询中的进度是已保存的nextIndex，不代表已经逐格验收旧建筑。崩溃落盘一致性、原地修缮和自动接受玩家补建均不在本轮范围。

## 旧施工任务安全补签名

升级或更换数据包前请先备份完整世界存档及原始蓝图。新施工任务保存 `v1-` 加64位小写十六进制的稳定指纹；它覆盖有序步骤及状态/耗材信息，同ID不意味着同一施工计划。改变蓝图内容后，已有签名任务暂停且保留原点和进度，**只能恢复与保存签名一致的原始蓝图后续建**；adopt不能覆盖已有签名。

旧存档没有指纹时显示“未核验”并暂停。站在目标聚落附近，以OP等级2玩家执行：

```text
/coop settlement construction
/coop settlement construction adopt <上条输出的当前指纹>
```

将尖括号及其内容替换成完整当前指纹。命令没有坐标、任务ID或跨聚落参数，仍只选择真实玩家所在维度64格内最近的已登记聚落。普通玩家只能查询，不能adopt；查询和失败的adopt均不补签名、不推进任务。

补签名仅接受未签名旧任务，当前蓝图必须存在、进度有效、输入指纹与当前蓝图精确一致。所有已完成步骤 `[0, nextIndex)` 必须全部处于已加载区块，并与当前蓝图对应的**完整方块状态**逐格一致；任一未加载或不匹配即拒绝，并给出失败位置。不强制加载区块、不接受只匹配方块种类，也不自动修复缺失或被修改的方块。`nextIndex=0` 没有已完成前缀可核验，仍需管理员明确选择当前指纹。

成功只写入当前签名，不改变原点、nextIndex、已放置方块或任何物品；没有退款、自动迁移或重开项目。此前的消耗历史及未完成的原始步骤无法由世界反推，前缀匹配**不能证明历史蓝图与当前蓝图完全一致**，也不能证明耗材历史一致。管理员应先核对备份及蓝图来源，再决定是否采用当前蓝图。补签名后仍可能因占位、缺料或其他施工限制暂停，不等于立即恢复施工或完成验收。

## 材料解释与边界

- 真实库存列出公仓全部物品ID与数量；抽象库存单独列出资源数量。两者不会重复算成同一库存。
- 只有当前蓝图与任务签名兼容时，当前施工才统计已保存 `nextIndex` 之后仍需消耗的物品；旧任务未核验、蓝图变更/缺失或进度无效时只显示阻断原因，不把当前蓝图需求当作旧任务的剩余需求。门/床的无需消耗续半块不重复计费。
- 每个待建项目独立计算缺口，没有预留或扣除其他项目的需求。原木制木棍、工作台制作等潜在转换不提前折算成已拥有物资。
- 建造缺口只计入当前可使用物资；抽象库存需要survival和production同时开启才能用于建造。
- 未登记公仓、公仓被移除/阻挡、所在或箱子水平邻块未加载时，不扫描或强制加载区块。仍可查看抽象库存与需求，但缺口显示未知，交接被拒绝。
- 命令同步运行在服务端线程，身份、位置、聚落、公仓全部由服务端解析。没有任意坐标、库存或批次ID参数。

## 自动化检查

`SettlementCommandsTest` 与 `SettlementConstructionCommandsTest` 覆盖施工查询/补签名的真实语法、OP2权限、指纹参数路由、格式拒绝、双语消息及只读格式化；另覆盖真实命令树的读写权限、开关/资源白名单、Tab补全、整数上下界、最近聚落范围、材料差额、导出批次顺序与满仓部分交接。运行方式：

```sh
./gradlew test --tests '*SettlementCommandsTest'
```

本增量不启动本地游戏服务器。游戏实测按以上流程统一执行。

## 备粮目标：储粮与其他劳动的取舍

`/coop settlement reserves` 只读查询；OP等级2可执行 `reserves normal` 或 `reserves high`。命令仍按真实玩家所在维度与64格范围选最近聚落。目标随聚落保存，旧存档缺字段或未知取值默认常规。它是玩家设置的有限劳动目标，不表示居民协商产生了新法律或社会制度。

- 常规为每名登记成员8食物点，加倍为16；模拟生存开启时分别折算为40/80模拟营养。人口包含登记儿童与暂未加载成员，沿用原储备口径。×5只用于目标尺度，不能据此换算具体物品；例如真实模式1颗甜浆果计1食物点，模拟模式同一颗计18营养。
- 关闭模拟时只读实际可访问公仓食物点；开启模拟时只读该聚落抽象公仓的可用营养，不把两套库存加在一起。真实仓库不可用时显示未知，而不是把未读取库存宣称为0。
- 只有既有FORAGER分工在仍有粮时按目标主动补储备。少于3名已加载成年成员时没有此分工；目标变高本身不会派出额外工人。真实缺粮时的应急觅食仍按旧规则，配额耗尽不等于公仓缺粮。
- 目标改变在下次选工生效，不中断已经开始的一次收获。它是停止线，末批收获可以超过目标；成熟作物、可达路径、背包空间、模式和劳动时间条件仍须满足。没有可收获目标时可以继续其他工作。
- 提高目标会让符合条件的觅食者优先继续补粮，推迟这名居民的其他行动机会；不代表全村停建，也不保证最终收成或总体建设速度一定如何。目标不锁粮、不扣料、不改每日配额或规范；面对面赠食按第二十七增量读取当前目标。

### 同条件对照（待用户实机验证）

先备份独立测试世界。登记3名已加载成年居民和公仓，开启survival与production，暂不开其他可选功能。导入10颗普通甜浆果，即180模拟营养；此时3人的常规目标120，加倍目标240。附近给觅食者准备可达的成熟浆果或已标记成熟马铃薯，并用村民交互观察其分工与动作。保证居民暂不饥饿，留意随后进食、腐败或收获可能改变库存。

1. 执行 `reserves normal` 后查询，应为180/120、缺口0，已有粮时不应单因储备而新发起收获。若已经开始收获，先让该次动作结束。
2. 在同一库存条件执行 `reserves high`，查询应为180/240、缺口60；觅食者下次选工应优先寻找可达成熟食物，实际收获后才增加库存。没有资源、模式关闭或背包已满时不能凭目标生成粮食。
3. 准备可继续的施工/加工条件，记录同一觅食者在两设置下的下一动作，其他居民仍按各自条件工作。比较行动机会，不只看某段时间最终产量。
4. 切回normal、重复设置、保存重进两次；目标应保留，设置本身不改变库存、事件、已领额度或正在施工的进度。换另一聚落核对目标不串营地。
5. 普通玩家可查询但不能改目标；离开所有聚落64格后命令不能创建新聚落。关闭survival后只看真实库存，未导出的抽象粮不被重复计入。

## 面对面赠粮与备粮反馈

普通玩家无需OP即可与已登记居民互动。非潜行右键查看当前动作、备粮目标、当前量、差额和单位；主手手持支持的普通食物、在4格内潜行右键，提出赠送一件食物。物理模式进入实际公仓，模拟生存模式进入抽象公仓；成功提示说明入公仓，不能当作该居民已立即进食。主手以外的相同物品、其他组件堆叠与副手不被这次赠粮消耗。

- 居民先考虑支持的食物与自身饱食，满腹仍可拒绝。低信任且状态舒适时，目标已满足可以拒绝；提高目标产生缺口后，同一居民可能愿意接受。既有信任、社交倾向仍然有效，不是目标一变所有人都必须听从。
- 生存模式只认当前抽象库存营养；真实箱中待导入食物不混计。实体模式只认可访问公仓食物点；仓库缺失、未加载或不可访问时显示不可用，不能据此断言实际库存为0。
- 每次成功仅交接1件，玩家真正付出物品，公仓和援助记忆在成功后改变。拒绝、满仓和槽位拒收不会制造物品或增加信任。定制组件食物仍不支持。
- 赠粮不改变当前件数额度、规范或社会形态；礼物记录也不等于私人占有公仓或取得劳动控制。未知旧记录不会被补写为当前目标。

### 可复现对照（待用户统一实机验证）

1. 先设 `reserves normal`：三人的目标120已满足。右键观察当前180/120、缺口0，然后用普通马铃薯潜行右键；舒适且低信任的居民应按已达目标拒绝，手中食物不变。
2. 保持库存与居民状态相同，改 `reserves high`：目标240、缺口60。再次递粮应能按缺口接受，当前主手减1颗，抽象公仓增加1件块茎/24营养，援助记忆增加；居民饥饿不因递粮动作直接下降。
3. 在另一背包格放同类食物，选中主手槽进行操作，核对只减主手；分别测试满腹居民、组件食品、远距离及副手，不能误消耗。实体模式另用满仓或拒收槽验证原槽保留。
4. 保存重进两次，核对目标、库存、信任和礼物记录；之后改变库存/目标，旧记录不能跟着变成新理由。援助次数也会保存，当前没有独立次数显示；旧存档缺字段默认为空，不回算过往次数。非潜行重复查看不应制造赠粮或信任事件。

这是运行时验收清单；本轮只运行无游戏服务器的编译与单元测试，不以此宣称交互、寻路或屏幕输出实机通过。

## 现场公仓会议

开启survival与norms后，日结仍处理本人遭遇的拒绝/短缺并形成已有规范提案，但不会把全村已加载居民自动当成与会者。普通玩家可用 `/coop settlement meeting` 只读检查；准备好后，在真实可用公仓4格内执行 `/coop settlement meeting hold`。

- 只有真实已加载且处于实体tick区域、仍存活、登记并已映射、处于公仓6格内的成年决策者可能参与；玩家不是投票者。沿用有效居民范围与同营地限制，不强制加载区块、不自动召集或寻路。
- 现场真实持有提案消息的人可介绍给同场合格成年人。只有能够形成至少两名有剩余社会工时的知情参与者时才提交会议；孤身、无人、无议题或工时不足不会先传播信息、扣时或刷轮次，可以等人后再试。
- 一次成功会议只推进一个确定的开放议题，每人支付1社会小时。每聚落每核心日最多成功一次；同日重复、保存重进或切开关都不能额外推进。刚跨游戏日且尚未完成日结时，先等日结再试，命令不会代跑日结。
- 参与率分母沿用日结范围：当前已加载、仍登记并映射、位于聚落中心64格内且核心可决策的成年人，不只数在仓边的人。居民按处境和关系形成立场，玩家不能命令赞成、直接修改额度或保证采纳；两名支持者面对10名有效成年人只有20%参与率，达不到原35%门槛。
- 本日议事成本进入下一核心日已有的采集/加工时间计算；不会立刻停工播放会议动画。采纳后仍沿用原配给与监督资格，不能据此宣称监督者已在Minecraft现场。
- 新现场事件保留当时地点、分母和真实投票依据；改变当前人口、立场或规范不会改写它。缺席的旧知情者不自动获得新结果。旧记录保持旧含义，不会补造现场证据。

### 统一实测路径（尚未运行游戏）

1. 备份独立存档，登记至少两名成年居民和可用公仓，开启survival与norms。使居民真实出现额度拒绝或持续短缺，等日结生成提案，再查询meeting与events；不要把单次查询当作已开会。
2. 只有一个合格知情者在仓旁时尝试hold，核对轮次、工时、消息与当日机会不变。让第二名合格成年人实际来到仓旁，再hold，应只推进一个议题一轮，参与者各付1小时。
3. 同日再次hold、连续保存重进两次、关闭再开启规范，均不能增加轮次。等下一核心日，再满足现场条件才可继续；同时观察原采集/加工时间成本。
4. 对照两名与十名有效成年人，仅让两名到场，核对分母与参与率。远处曾知情居民不能被计作本次赞反票，也不能被标为已听到新的采纳结果。
5. 检查玩家太远/旁观、仓库不可用、居民离场或卸载、成员归属改变、剩余社交工时耗尽，均不应错误收费或造会议。空议题和失败后补齐条件应仍可成功。
6. 查阅本功能新记录的一次既往现场会议，改变当下人口、提案立场与库存后再查，冻结的历史证据不变。旧版无现场标记的规范记录保留旧投影语义，不能当作现场证据。会议本身不移动或消耗食物，采纳后下一次真实进食才按规则结算。

完整自动验证结果见开发记录；客户端交互、真实容器/实体门禁、调度和屏幕输出仍需上述统一实测。


### 看懂议题和本轮结果（第二十九增量）

现有 `meeting` / `meeting hold` 增加说明，不新增投票或直接选政策的命令。会前说明使用现场检查实际选中的提案：基本口粮保障的参数是每日基础食物件数上限，老幼照料优先的参数是需要照护者的额外件数；后者不是全员加额，也不单独改变到仓排序。没有有效提案或未知规则时，不猜测可执行政策。

- 现行基础默认3件。首次采纳基础上限2件可能把上限从3降至2；历史中的旧规范参数0只代表此前尚未设立该规范，绝不能读成居民原来无权领粮。已有当日领取不因查询、开会或额度调整而退款或清零。
- 每轮回执只引用本次真实讨论的事件，显示当时的参与、赞反、原因或规范参数变化。首轮“继续协商”并不总是支持不足；原规则至少需要两轮，并检查参与比例、支持比例、家庭立场和付费后的监督资格。只读查询不预测居民的下一票。
- 当前件数额度与需求排序分开：ACTIVE规则可改变额度，但需求优先窗口还需要两名同营地、有剩余社会工时的核心支持者。此资格不是Minecraft实体现场监管。照护额仅影响 `needsCare` 居民；关闭相关功能时，保存的规范不能被描述为正在执行。
- 件数不是营养，不保证仓里有粮，也不保证居民已经吃到。会后用 `/coop settlement rations` 对照个人上限、已领、剩余与实际营养，再用 `/coop settlement events` 对照会议和后续分配。开会本身不预留、不发放、不消耗食物，每个实际参与者付出的1社会小时仍按原规则影响下一日采集/制作。

统一实测时，分别检查首轮继续、参与不足、支持不足、付费后监督不足和第二轮采纳；让基础规则与照护规则分别作为实际选中议题，对照文案的单位和适用对象。成功后重复meeting查询、保存重进、耗尽监督工时和关闭模式，核对当前效果随条件变化；用events重查当轮冻结记录，票数不被当前立场重算。重复meeting只显示今日会期已用和当前效果，不重放上次回执。聊天排版、真正到仓领取及实际画面仍待用户测试，不以自动化断言代替实机验收。


## 面对面邀请居民赴会（第三十增量）

会议说明能展示议题和到场人数，但此前没有请居民前往公仓的动作。本轮新增单人邀请：主手空手、潜行，在4格内右键已登记成年居民。手持食物潜行仍是原赠粮；非潜行仍检查。邀请者可以再次空手潜行点同一居民取消，其他玩家不能接管一份有效邀请。

邀请不是讨论，也不是投赞成票。它不会创建提案、传播提案知识、扣社交工时或移动粮食；仍需至少一位符合原会议知情条件的居民到场。通过普通检视核对居民是否知道开放议题，以及应邀等待当前动作、正在赴会或已经到场的状态。居民先完成已经开始的普通工作，再将赴会作为下一项行动；实际进食和饥饿需要优先。

- 必须开启survival与norms，日结已完成、今日会期未用，且有开放议题。只有真实存活、可决策、有剩余社交工时、登记映射正确且在当前聚落有效范围内的居民可被邀请；幼体、受伤、睡眠、交易、骑乘或NoAI实体不适合赴会。
- 核心饱食度不高于35时拒绝或取消，不因仓里无粮而忽视饥饿。正在进食或等待取粮的居民不接新邀请。
- 邀请从接受起总计最多1200 game tick；开始赴会后旅行另限400 tick，到场后最多等待600 tick，且都不超过原总截止（20TPS时分别约60、20、30秒）。接受、走路或等候都不会延长截止，取消后需重新面对面邀请。不传送，不强制加载区块，不保证原版AI和所有地形都能成功寻路。
- 居民沿实际可站立路径接近真实公仓，实际距仓中心3格内才进入等候；导航成功返回值不当作已经到场。原会议仍独立检查6格在场资格，玩家须到4格内执行meeting hold。赴会与等候占用该居民的行动机会，只有真正讨论时才按原规则扣1社会小时。
- 邀请只在内存中。跨游戏日或核心日、模式切换、公仓重新登记或箱体结构/身份失效、成员或映射改变、实体卸载、邀请者不可用及成功开会均使旧邀请失效；保存重进必须重新邀请。已有日会期和已完成配给仍照原格式保存。失效后检视显示暂无有效邀请，不保存一份取消历史；需要重新面对面邀请。

### 统一实测流程（未启动游戏）

1. 用备份测试存档准备两名不饥饿、健康的成人、可用公仓和真实开放提案。居民开始时距仓超过6格，至少一人知道提案。逐人空手潜行邀请，检查接受只改变赴会状态，不立即增加轮次、知情者、社交小时或库存。
2. 对正在采集或制作的居民邀请，核对先完成本次工作且只扣一次材料/产出一次；然后实际步行到仓。另一居民正在进食或等候取粮时邀请应被拒绝，不能取消其已准备好的餐。
3. 看见两人真实到仓等候后，玩家走到公仓4格内，先查meeting再hold。没有hold时不应自动讨论；成功后只推进原规则允许的一轮，随后居民结束等候恢复普通行动。
4. 分别用围墙阻断远处通路、替换箱子、改变双箱结构、让区块停止更新或卸载居民，核对没有传送、远程参会、无限重试或恢复旧邀请。桶盖正常开合不单独使邀请失效。
5. 在赶路和等候时分别测试饥饿、受伤、交易/睡眠、推离等候位置、邀请者离线/换维度、到期及跨日；查看取消结果后再按正常条件重新邀请。再次空手潜行取消自己的邀请，其他玩家重复点击不能延时或接管。
6. 保存重进、关开规范、公仓A→B→A以及移出再登记同一成员，都不能延续旧票。邀请不入NBT，原库存、领取次数、会议历史和会期保持兼容。

自动化只能覆盖共享门禁、票据生命周期、保存数据与消息参数；真实World/Goal调度、原版Brain竞争、寻路、屏幕输出和多人到场仍按上述流程统一验收。

## 会前询问居民意见（第三十一增量）

开启survival与norms后，普通右键检视登记居民，会针对本营地按提出日期、议题ID排序的最早开放议题作简短询问。内容明确标出议题ID、规则和参数，不再把“知道任意一个议题”当作知道当前询问的议题。现场 `meeting` 仍按实际参与者选择可讨论议题，因此询问的最早议题不一定是下一次会议处理的议题；组织前应对照两处ID。

- 不知道这条议题时明确显示未知，不给出虚构支持票，也不因玩家查看而传播。知道议题与持有可靠介绍消息分别显示：消息被淘汰、可信度不足或来源不匹配时，保留已有知情，但不能据此介绍给别人。
- 已知且核心可决策的居民展示“此刻倾向”及实际计算依据，包括本人和家庭的饥饿、互助认识、不满、对提议者的信任及家庭储备利益。它与实际会议使用同一公式；饥饿、库存或关系变化后倾向可变，不承诺之后投同一票。保存的立场不被查询覆盖。
- 核心决策资格与剩余社会工时限制介绍能力。这不是已到场证明，也不保证赴会邀请被接受：实体健康、进食、通路和时间限制仍按前节执行。日结待处理时不把旧记录当作即时可用的会议资格。
- 询问不扣社会工时、不改知情、事件、轮次、会期、资源或领取额度。玩家据此选择邀请对象；真正满足现场条件并执行hold时，原会议才传播提案、重新计算立场并收费。

### 统一实测对照（未启动游戏）

1. 准备真实开放议题与两名合格成年人，先询问提议者和尚未听说议题的人，核对同一议题ID分别显示知情与未知。连续查看不能让后者自动知情。
2. 根据介绍能力选择邀请对象，实际赴仓后对照meeting选中的ID再hold。只有真实参与者获得本次介绍与会议结果；再次询问可看到他们现在已知及当前倾向。
3. 有多个议题时，用只知道较晚议题的居民核对最早议题仍显示未知。不要把不同ID的问询与会议结果混作一次意见变化。
4. 让食物消耗等真实处境变化后再问，当前倾向允许变化；已有历史会议票数不能跟着变。预算耗尽、幼年或核心健康不足时不能误报可介绍；关闭模式、跨日待结算、缺映射和保存重进也不应刷出免费知识或工时。

自动回归验证共享核心公式、只读适配、翻译参数与存档守恒。真实右键、聊天可读性、邀请及会议全流程仍待游戏验收。

## 登记归属与在场范围（第三十二增量）

同一维度内，成员身份由登记记录决定。右键钟重新扫描只接纳尚无归属的有效候选；已属本营的成员保留原记录，其他聚落成员不会被改籍。暂时走出64格或区块卸载不会因为再次敲钟而失去成员身份。面板的当前居民、阶段初始化人口、命名和核心映射只使用本次确认属于本营的有效候选，不能把外营访客当作本营人口。

- 新聚落仍需32格内至少两名候选，现只计尚未登记、存活、同维度且实际加载的村民。有残缺归属记录者也不被当作无主居民自动覆盖。
- 现有聚落登记扫描范围仍为64格。重复扫描不会改入籍日、人格、已有需求与核心人物，也不会单因再次登记而取消有效的取粮票或赴会邀请。距离限制决定本次在场名单，不等于成员退出。
- 明确移除仍按原路径取消票据并清名册、首领引用和实体模式需求，保留模拟人物及其历史。当前没有玩家转营命令；移除后到另一营重新登记不代表亲属、私人库存或经历已迁移，不能把它当作迁营工具。
- 稳定登记本身不修改原版交易表、职业、交易经验或既有自定义名字。专属居民界面和原版交易隔离尚未在这一增量接入。
- **本轮只保证同维度登记边界。** 存档仍按ServerLevel分开；跨维度归属解析、跨维度死亡的旧名册清理和资产迁移不在本轮范围。保留远行身份也不等于全部工作AI自动停止，既有日结及工作范围仍各按原机制执行。

### 统一实测路径（未启动游戏）

自动化覆盖生产共用登记/候选逻辑、票据身份和存档守恒；真实实体扫描、命名、钟面板和交易数据对照仍待统一游戏验收。


## 居民独立互动初版与交易隔离（第三十三增量）

本轮是**聊天式交互初版，不是独立GUI窗口**。普通主手右键本地成员继续显示需求、工作、备粮与会议意见，但不再顺势打开原版交易。主手持食物潜行右键仍提议赠送1件；主手空手潜行右键仍邀请/取消赴会。副手不重复执行这些操作。儿童、无职业或关闭模拟的登记成员仍是成员，动作能否进行另按原资格检查。

- 名称牌、刷怪蛋和原版上游物品处理保留原顺序，成功后不再进入居民快捷动作。非成员保持原版交互。未成功的村民刷怪蛋沿原版分支处理，也不会借该分支打开原版交易。
- 成员原版交易请求被拦截，保留职业、等级、基础交易表和经验。若登记时已经打开交易菜单，下一笔原版选配方/点击请求先被拒绝，下一次玩家tick按原版正常关窗。付款槽和鼠标携带物走原版返还/落地流程，不发放结果预览；正常关窗可能清除本次顾客临时折扣。
- 普通查看没有新增窗口、刷新按钮或网络会话。本轮不增加市场、货币、雇佣，也不让赠粮与意见查询替代真实生产或讨论。

### 维度与归属边界

右键、交易菜单、创始人数、钟扫描和出生登记，读取服务器当前提供的各ServerLevel成员记录。归属以“维度＋聚落ID”为边界，不靠距离、模拟开关、工作阶段或核心Person是否存在判断。每次操作重新解析，不保存全局索引，也不加载居民区块。

- 只有全局无claim候选才能新登记；唯一本地本营记录可幂等使用。异维度成员不能成为新创始者或被钟扫描认领，出生前也要确认双方父母均唯一本地同营、孩子无已有claim。
- 唯一异维度成员只显示家园与外出信息，不能把家园数据交给当前维度的赠粮、工作、仓库或邀请操作；仍不回落原版交易。
- 孤立归属、多个归属或明确无法读取来源集合时显示诊断，拒绝自动重认领和交易。不会擅自选择一营或“修复”旧冲突；没有玩家迁营/修档命令。
- 只有观察到真实死亡时，才将原有名册移除路由到唯一原始claim所在维度，包括唯一孤立记录；冲突或不可确认时不批量删除。历史Person、资源、亲属和事件保留。卸载、传送、暂时找不到居民和查看资料都不是死亡。
- 只覆盖当前服务器提供的维度，不扫描已移除维度的磁盘存档。原版存储层可能吞掉损坏/不可读数据文件的异常并返回空数据，本轮未重写存储层，不能保证在这种情况下识别丢失的旧claim。保留备份，勿把此功能当作损坏存档修复工具。
- 不实现跨维度工作、家户/资产迁移、僵尸转化与治愈的UUID衔接。交易守卫覆盖官方1.21.1玩家网络路径，不保证第三方模组直接调用菜单内部方法。

### 统一实测路径（未启动游戏）

3. 先与未登记村民交易，在付款槽放两种付款、鼠标拿物品，再让其登记。测试关窗前的选配方、普通点击和Shift-click：不得再得到一笔商品，已放入的付款及鼠标物品只能按原版规则返还一次。背包满、断线和死亡条件分别对照；原职业、基础报价和经验不能清空。

## 独立居民窗口（第三十四增量）

本轮在第三十三增量的交互与交易隔离上接入真正独立窗口。使用双方支持新协议的客户端和服务器，普通主手右键唯一本地登记成员即可打开。正文可滚动，四个动作与关闭按钮固定；窗口不暂停世界，居民仍会行动、进食或离开。客户端不支持窗口协议时保留原聊天查看，不恢复原版交易。

- 窗口显示已有需求、工作、储备、邀请状态与当前议题意见，不增加新统计或虚构市场。点击“刷新”读取最新信息，不免费增加知情、社会工时或邀请期限。
- “尝试赠送当前主手中的1件食物”在服务器执行时读取实际当前主手，不以打开窗口时的物品图标扣物。居民仍按原服务决定是否接受，拒绝不扣；不支持的食物或组件有禁用说明。
- “发出邀请”是明确邀请，不会因为已有邀请而反向取消。“取消邀请”只针对上次展示的、当前玩家拥有的同一张票；票已过期、替换或属于其他人时拒绝。潜行空手快捷方式仍沿原邀请/取消切换习惯。
- 页面上的当前意见不是投票，邀请登记不是已经到场。居民仍须按原行动实际赴会，玩家仍通过原meeting hold组织讨论。

### 会话安全与生命周期

打开和每次动作都重验玩家、维度、实际居民对象、全局唯一本地归属及原成员对象，要求存活、非旁观、居民实际加载并ticking、4格内且视线畅通，不睡眠/交易；操作时不能另开真实容器菜单。移除再登记、传送、卸载、死亡或同UUID换实体不能续用旧窗口。视线检查前只读核对短距离射线区域已加载，不主动加载区块。

服务端每玩家只保留一份临时会话，绑定随机token和连续请求号；先认领请求再执行动作，重复或过时请求不能重做赠送/邀请。客户端一次只等待一个动作确认，既不自动重发赠送，也不把本地按钮状态当授权。关闭是独立终止；失效、断线、停服及2400游戏tick无有效操作（正常20TPS约120秒）会清理会话，不写入NBT，DataVersion仍19。

新窗口打开前若存在真实菜单，使用原版closeContainer处理付款、携带物和关闭，不直接清槽或手工补偿。刷新只更新当前同一窗口；旧更新、旧关闭和重复打开消息不能恢复已关闭窗口或关闭后来打开的界面。世界实例改变、死亡和断线会清理客户端状态。极端超长或过深的文本/样式会被协议边界拒绝，不把异常视图当成成功操作。

### 统一实测路径（未启动游戏）

## 居民窗口召开仓库会议（第三十五增量）

在邀请居民赴会后，可直接通过居民窗口的“召开会议”完成现场讨论，不再必须输入命令。玩家仍须在真实公仓中心4格内；会话另要求与正在交谈的居民4格内且视线畅通。公仓中心6格内的合格成年居民按原规则参与，邀请不是出席证明，窗口对应居民也不自动获得发言或投票资格。

1. **先核对实际议题**：窗口上部显示本次可以推进的议题、拟改变的额度、当前合格人数/活跃成人、轮次与地点。这个议题可能不同于下方个人意见区固定查询的最早开放议题，以明确ID区分。
2. **选择现在开会或继续邀请**：有效会议花费每位实际参加者1社交小时，占用本聚落当前核心日唯一会期。工时仍沿原机制影响次日采集/制作；没有新增即时统一停工扣时。每轮不保证通过，玩家不指定意见、票数、额度或参加名单。
3. **审阅变化就停下**：服务端只接受上次完整展示的可执行预览。议题/额度/轮次、核心日与游戏日、模式关开、仓库绑定或实际容器、居民对象与资格、现场人选等变化会拒绝本次召开，并返回刷新后的信息供重新核对。人数相同但换人也不能静默执行。当前不具备条件则显示真实原因，不扣工时、不占会期。
4. **核对真实结果**：成功后保存本窗口最近一场会议的冻结事件回执、轮次、结果与会后即时规则；刷新不会把它改写成下一议题或重开会议。关闭窗口不删除核心事件，历史仍可由 `/coop settlement events` 查看。
5. **继续观察取粮**：窗口同时显示这位居民的现存核心日、已领/上限/剩余件数、已领食物营养与饥饿。未完成当前日结算时明确标记；没有旧营养证据就显示未知，不补造。会后仍由居民自己走到公仓取粮，额度与营养不是同一量，会议不创造、预留、消耗或发放食物。

## 完工前的床位加载复核（第五十二增量）

这项检查只要求登记结果可判断，并不提前登记床。已加载但损坏或缺失的床继续返回无效，完工后不会凭空增加容量；不自动修复，也不把工程变成维修任务。最后一步本身是床头时，放置前已加载但尚不完整的床允许继续，之后仍由真正登记服务验证两半。已有其他聚落的床仍按原归属规则处理。

## 在公仓旁徒手准备首台

若聚落仍缺床、没有任何登记工作台、没有在建工程，且当前首台蓝图保持受支持的单台结构，居民可在公仓旁进行两轮各需制作时间的操作：**1根普通橡木原木 → 4块橡木板 → 1个工作台**。也可直接投入4块普通橡木板或成品台。居民右键信息显示“在公仓旁徒手准备首个工作台”；制作完成产物仍在真实公仓，后续独立施工完成后才登记设施。不会远程放台或凭制作增加床位。

- 这是首台专用需求，床、门、营火、工具等仍要求原来的加工设施。已有任何工作台登记即不启用，即使它远处、失效或未加载；任何已有施工任务也不启用，包括缺料、未签名、蓝图改变以及已开工的打制点。既有工程需要补回缺失成品，不会偷偷改成自举流程。
- 仍优先满足已有进食、采食、会议和可施工机会；材料齐备且能选址的住宅会先按原逻辑启动，首台制作不抢走它的材料。每轮使用原制作时间、性格、饥饿、技能和社交时间倍率；不是立即合成。已接受邀请时沿用完成当前批次再赴会的行为。
- 公仓须为已加载且处于实体活动区块的普通箱子或木桶；双箱两半须完整有效。劳动期间绑定实际方块实体和连接形态，普通开关桶盖不取消，替换/拆除/改绑或另一半不可用会失效。最终必须在公仓3格交互范围内重新核验、重新取容器、重新选择配方才扣料。
- 一轮的配方被别人完成、已放入成品台、床补齐、新工程启动、成员归属或蓝图改变后，旧操作不能误扣材料；重复执行同一轮不会重复产出。别人中途投入成品台时动作可能显示到当前批次结束，最终拒绝而不消耗原料。只要公仓有可施工的工作台，就不继续徒手产台；没有安全工地也最多留下一个成品等待。

- 两轮成功制作可分别留下原有制作事件和技能记录（需相应开关及映射）；失败不记成功，公仓成品不重复导入抽象库存。票据仅内存存在，读档从新机会重新开始，未增加存档字段。

## 以线补足木屋床的羊毛

居民在原有可用工作台旁制作建筑材料时，白床不足且普通白羊毛不足一床的3个，会尝试每批消耗4根普通线、得到1个白羊毛。已有羊毛优先使用；最多备到下一张床所需的3个，再等木板或制作床，不因大量线无限囤毛。每批按原加工工时执行，结束时重查需求；制作/技能事件仍走原有记录。白床成品按可领取的普通实物计数，满足需求便不再为了该床制作或追加原木需求；命名/带组件或施工用途标记的床，以及命名/带组件的线和羊毛，不当普通供料。

这提供原版配方已有的替代原料路径。编织原料线仍须外部投入登记公仓；白羊毛也可来自后续逐羊许可剪毛。不会攻击蜘蛛、染色或从私人背包取料。没有实际可用的登记工作台，不会用本配方徒手加工；首台工作台的专用动作仅保持原木→木板→工作台。羊毛、线和床没有新增抽象资源映射，产物只在真实公仓；已有job、蓝图签名和存档格式不变。

`/coop settlement materials`（及status的材料部分）现在为每个项目的剩余白床显示原料预算：先减公仓可施工白床，再计算缺少的普通白羊毛及相当的总线量，并单列公仓现有普通线。两个床、没有现成床/羊毛时显示6羊毛或24根线；已有一床和2羊毛时显示还需1羊毛或4线。这里线预算是“替代缺毛的总用量”，不是扣现有线后的待补数；预算不预留、不合并不同项目，也不证明工作台/空槽/工地当前可用。公仓无法读取时继续显示未知，不把未知算成零库存。

木料链也有清楚边界：只采居民12格搜索范围内、归属有效的已标记木石块，标记不是整树授权，采完该格会移除标记；没有自动识别未标树、补种或可持续林场。羊毛、线、煤/木炭继续外供。这些限制会在有施工或待建项目的材料查询中提示。

## 木石实物返仓与材料遗物

这一轮改变的是非食物材料的交付：运行时LOGS标签里的原木、圆石、木棍、平滑石。新采集物和居民私人制作的这些产物先留在实体原有8格背包，不再采完/做好立即扣进公共抽象库存，也不再由40tick轮转从64格范围自动上缴。公共工作台直接在公仓制作的门床等产物仍在公仓；旧抽象资源批次与已有显式import/export不迁移、不复制。

有上述货物的成年居民会优先选择“携带材料返回公仓”，实际寻路到仓库同高四个面邻格之一。该格要求脚头空气、安全完整支撑、范围合法且已加载/ticking；真正卸货前再确认实际站位、3格距离、当前唯一成员归属和原仓实体/双箱绑定。箱子换掉、重绑A→B→A、任一箱半卸载、成员换归属等会取消旧票。只有实仓接纳的数量才从背包扣去；满仓剩余留身上，不额外生成可消费抽象批次。

每20tick最多尝试2条路径，每轮仅4个邻格；失败后100tick再试，单次行程最多200tick。路径创建前检查搜索区域已加载，路径节点也检查加载/ticking，不强加载。普通进食、会面和低饱腹急救仍有优先权；带货时不继续一般木石采集。暂停原因会显示仓储不可用、无安全可达邻格或无接收空间。四邻同高是保守首版：抬高/下沉/仅台阶可站的仓库可能需要玩家整理平整入口；本轮不自动挖地或修路，也不保证任意布局可达。

正常卸载和保存/加载仍以原版实体Inventory为在途货物权威，瞬时返仓票可丢弃，回来后按实际背包重建。货物跟随实体，成员改营地后只能给当前新营地交货；未另建原产地货权账。这与旧后台上缴不同，不表示已经实现阶级、雇佣或运输制度。

### 死亡材料的保全和领取

- 同维度死亡点64格内玩家收到一次提示。`/coop settlement cargo` 列最近8份、64格内的未领记录，含位置、材料计数和记录ID，不要求死者仍在名册。

- 接纳多少领多少；背包满则保留遗物，部分领取后可再来，领完删空记录。任何到场玩家均可领取，类似公共地面遗物，本版没有私人锁或自动替居民交仓。
- 遗物存独立SavedData，现有文明NBT版本与旧工程不改。未知版本或明显损坏数据原样保留、禁止捕获/领取并告警，不悄悄当空档覆盖。正常存档往返保留物品components；跨实体/区块/玩家文件并非原子事务，不能承诺断电或进程崩溃下绝无复制/损失。

## 普通实体模式的多余采集食物返仓

本阶段只改变 **survival关闭** 时的甜浆果与马铃薯：采集后先留在居民真实背包，保留个人口粮，超过保留量的部分走已有返仓路线。小份采集可能全留个人，不保证每采一株就回仓；也没有标记“这颗是谁采的”，同类既有实物按相同口粮规则处理。

- 口粮阈值继续取人格对应的foodRetentionPoints，最低12食物点，且不低于基础口粮领取目标。以全部真实食物计算剩余点数，只上缴浆果/土豆的整件超额。混合面包等高点数食物仍按原点数计，不额外征收保留份。
- 检测与卸货用同一计算；实际到公仓安全邻格时重新看背包，途中吃掉的数量不会按旧票补发。旧40tick维护不再远程收这两种食物，基础口粮配发和其他食物的原处理仍保留，因此这不是整个食物系统都已改成搬运。
- 真实箱满则留余粮，部分接纳只扣实际接纳量；命名/带组件堆叠原样交付，不混成普通食物。无安全入口、换仓、卸载、归属变化沿材料返仓的取消/退避边界。携粮返仓不会新增抽象批次或立刻增加模拟饱腹。
- 票据记录当次模拟状态对象及现有模式版本。开启survival再关闭也不能复用旧票；正常重载后以真实背包与当前模式重试，不保留数量预约。进入survival后现有个人食物不自动导入公共口粮，须依该模式既有赠送/import流程处理。
- 普通模式成员死亡时，背包余下的浆果/土豆（包括原个人保留量）也进入现有遗物记录，组件保留，可用cargo命令到场领取。其他食品与survival实体食物不扩大死亡处理范围；原未知坏档、特殊转化、进程崩溃限制仍适用。

**为何暂不改变survival的采集入库：** 该模式仍在采收时扣实际食物并生成公共抽象口粮，之后按既有批次腐坏。当前导入接口以入库日生成采收日与到期日，直接延后到仓会把运输等待变成保鲜时间；还需防止空公共口粮时紧急觅食抢占已有粮食的返仓。因此后续应先引入可保存的采收年龄与过期处理，再接入运输。本轮不修改其库存权威、腐坏时钟、配给或既有采后上缴，不声称survival食物物流已完成。普通实体食物延续原版无腐坏计时的行为。

## 显式食品交接保留采收日期

## 带年龄食品的原版消费隔离

- 玩家悬停时有中英文货物提示。可搬动、保存、领取遗物并通过已有管理员import导回来源聚落；来源/年龄验证继续按第五十九增量执行。开关survival不解除隔离，不重写任何旧堆的标签。

- 村民不拾取这种掉落货物。已在居民背包内的货物不计入原版繁殖口粮，也不会被原版吃掉、分享或种植；同一背包中后面的普通食物仍可正常使用。守卫仅返回只读的空视图，不清空或改写原槽位。原版分享会新建无组件物品，故必须在扣原物之前跳过。

## Survival甜浆果的采收返仓首轮

4. 到仓时，按**当次真实箱子快照**一次规划浆果接收量，遵守槽位、最大堆叠数和完整组件匹配；多批次不能反复利用同一空位。满箱收0，部分接纳只扣对应背包槽的实际数量，余量保留原年龄。预检全部入库参数和编号空间后再次检查到达、身份、模式与容器未变，旧票据不可重放。
5. 接收量从背包直接转成保龄公共模拟批次，箱内已有食品和材料不动，也不另留一份同批浆果。**箱子只作为当次卸货的临时接收门槛，既有模拟总粮容量仍无上限**，这不是常驻实体粮仓容量系统。后续一次新的返仓尝试可重新检查容量，不能把本实现当作一次性永久空间预约。

## 土豆留种、保龄返仓与副产物边界

第六十二增量把survival和production同时开启时，**明确标记的成熟土豆地块**接入同一真实返仓。新采收的普通甜浆果与土豆都先留在实体背包，走到当前公仓安全邻格后才转为公共口粮；原有普通模式余粮规则不变。

- 先从本次原始掉落取1粒普通土豆用于原地再种，再给剩余普通土豆标采收日期。背包旧物、定制土豆、已标龄土豆与毒土豆不能替代这粒种子。缺少种子就不采收；恰好一粒可以再种，但不增加食物或实践次数。
- 净产出与毒土豆/定制副产物须全部放得进背包，才改变成熟作物。旧普通栈不能与新标龄栈合并，不会为腾位置把副产物删掉。地块标记、成熟度、加载、居民身份、模式或日期发生变化时取消未完成采收。
- 到仓后土豆与浆果共用一次食品接收计划，遵守完整组件匹配与真实剩余槽位；已由一种食品占用的临时空槽不能又供另一种食品使用。接受多少才扣多少背包，箱内旧物不动，公共库存不留第二份实物。土豆保存原8日、浆果原3日保鲜边界，期满当天仍有效，之后拒收并保留原货物。
- 食品入库仍没有总模拟库存容量上限，箱仅是每次卸货的临时门槛；食品和材料是不同接收步骤。鱼肉等其他来源、施工取料与整套物流还未统一。旧通用生产导入接口保留，但新的土豆世界采收不会再调用它。

## 已付门床续步与施工取料进度

工程变更或被其他工人抢先后显示“将失效施工余料搬回公仓”；满仓、无路或暂停保留背包原物。来源、居民、维度不明或标记损坏时不自动解绑定。死亡物可沿现有cargo命令领取，保留原用途；公仓不会当作新任务的普通门床。命名/其他定制门床也不再自动征用。材料/羊毛需求按可领取的普通库存计算，施工总诊断尚不统计在途材料。

旧工程加载时增加稳定实例ID，位置、进度、指纹不变；字段损坏时显示暂停原因，不能靠认领图纸重建许可。升级前备份整个世界，勿让旧版本回写新用途/任务身份。以上已做自动服务验证的结果见开发记录，真实导航和世界表现仍待游戏验收。
