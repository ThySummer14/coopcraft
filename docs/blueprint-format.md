# 小型建筑蓝图格式与边界

位置：`data/<命名空间>/civilization/blueprints/<名称>.json`。资源路径决定蓝图ID，例如路径 `data/coopcraft/civilization/blueprints/stone_cottage.json` 对应 `coopcraft:stone_cottage`。JSON中的 `id` 可以省略；填写时必须与资源路径一致。

当前规划器主动选择 `coopcraft:campfire_hearth`，并在存在床位缺口时选择一款版本化木屋：`coopcraft:timber_porch_cabin_v1` 或 `coopcraft:timber_side_porch_cabin_v1`。已登记床位每两张切换一次，0/1床从北廊开始；旧 `coopcraft:stone_cottage` 保留给已存工程。新增合法文件不等于已新增规划规则，也不会立即在世界中放置建筑。

## 格式

| 字段 | 约束 |
| --- | --- |
| `size` | 恰好三个整数，按X/Y/Z排列，每轴1–64；省略时兼容旧默认 `[5,4,5]` |
| `layers` | 可省略；最多64层，每层指定 `type`、`y`、`block` |
| `type` | 仅 `floor`（整层）或 `perimeter`（四边） |
| `y` | 整数，范围为0至size的Y值减一 |
| `special` | 可省略；每项含 `pos` 与 `block`，同坐标不能重复声明 |
| `pos` | 恰好三个整数，均在声明尺寸内 |
| `block` | 已注册方块ID，可带合法属性，例如 `minecraft:oak_door[facing=north,half=lower]` |

尺寸与坐标只接受JSON整数写法，不接受字符串、小数或指数写法。

图层依声明顺序生成，后来的图层可以覆盖前面的同坐标。special替换对应图层后移动到施工序列末尾，再按special的声明顺序施工。最终序列必须非空且最多4096个位置；限制是当前小建筑的解析与运行预算，不是完整城市建筑系统的上限设计。

未知方块、属性或属性值，错误括号语法及重复属性名会报错。空气及没有对应可放置物品的方块（如水）不能成为施工指令；本格式没有把air解释为挖空或删格，空位应不生成指令。错误包含蓝图ID；与布局有关的错误还给出位置，便于修正数据包。

## 门与床

门和床必须在最终布局中保留完整两半，不能只写一个免费的上半或床头：

- 门下半在前、上半紧接其后；上半位于下半正上方，同种门，除half之外的状态一致。
- 床脚在前、床头紧接其后；床头位于床脚facing方向的相邻位置，同颜色/种类，除part之外的状态一致。
- 每对只收费一次；来自图层还是special不影响计料。
- 覆盖掉另一半、错位、错向、倒序或在两半之间插入别的施工步骤都会拒绝加载。不会静默移动作者的步骤。
- 本执行器尚未支持双格植物等其他共享half/part属性的多方块放置方式，因此明确拒绝这些蓝图部件。

示例仅演示结构，文件名决定ID：

```json
{
  "size": [2, 2, 1],
  "layers": [
    {"type": "floor", "y": 0, "block": "minecraft:oak_planks"}
  ],
  "special": [
    {"pos": [0, 1, 0], "block": "minecraft:white_bed[facing=east,part=foot]"},
    {"pos": [1, 1, 0], "block": "minecraft:white_bed[facing=east,part=head]"}
  ]
}
```

此例为4个施工步骤、2块橡木板和1张白床。它不是完整住宅验收标准。

## 资源与重载边界

- 校验解决的是尺寸、ID、布局与门床的执行前提，不等于支持任意方块状态的材料经济。双层台阶、多蜡烛/海泡菜、含水量、生长阶段等状态的额外成本尚未统一建模；先使用当前已验证蓝图的部件，不要据此宣称任意状态都已守恒。
- 只在完整蓝图集合成功解析后替换当前蓝图库；一份无效蓝图不能让本管理器只换一半新数据。此保证不等于Minecraft所有资源重载器的跨系统事务。
- 新任务保存蓝图ID、原点、nextIndex和稳定计划指纹。指纹包含ID、有序坐标、完整方块状态及物品/扣料信息；同ID换布局、重排或改状态会暂停保留任务，不自动套用旧进度。缺失、索引越界也暂停；恢复与保存指纹一致的原始蓝图才可续建。无指纹旧job需管理员显式核验已完成前缀并补签名，见[安全补签名](settlement-commands.md#旧施工任务安全补签名)。它不能修改已有签名，也不能证明全部历史耗材。
- 此轮不改存档格式，不自动迁移已有工地，不验证寻路、地形、睡眠占用或整栋房屋可达性。

## 升级、恢复与回滚

- 当前存档dataVersion为19，新变体不增加字段或自动迁移。第三十九增量的新事件一旦写入，旧版本不能可靠降级读取；升级前停止游戏/服务端并备份整个世界目录和旧mod jar，包含区块、容器及聚落数据，不能只备份一个文件。
- 数据包配置错误时先恢复原始蓝图内容；有施工任务时不要用新布局猜测修补旧index。暂不可用任务及原点/index会保留，查询不会重置。
- 若需退回旧模组，最稳妥方式是停服后成套恢复升级前的世界备份及旧jar，再开服。不要一边运行一边替换存档，也不要混用新旧两个coopcraft jar。
- 备份后产生的新世界进展不会被自动合并回旧备份；本轮没有提供跨版本存档合并或崩溃事务恢复工具。

运行编译与单测：`./gradlew build`。本轮未启动游戏或GameTest服务器，实际施工仍由统一游戏测试验收。


## 已验证静态木屋约束

北向前廊与东向侧廊使用不同的版本ID，不在job里保存动态旋转。两款均7×7×5、154步骤、151份付费材料，按显式special顺序放置完整地板、墙柱、配对门床、受支撑火把和屋顶。东廊门两半显式使用相同右铰链，门朝东、两床朝西；不能只变换坐标而保留旧朝向。两款材料相同并不意味着签名相同。

新住宅须通过全部地基支撑、完整包围体净空与选定门外落脚检查；候选仅中心四向6/12/18格的同高、上下一格，合计至多36。没有针对不同朝向的自动回退。蓝图解析成功只证明格式及配对成立，完整静态检查和材料回归也不能代替游戏导航、落块及视觉验收。
