## 0. 核心任务：多个需要同时存在时如何做选择

同一个营地可能同时面临：
1. 公仓食物不足，居民寻找食物；
2. 幼儿需要照料，相关成员暂时无法离营；
3. 建筑缺少床位或材料；
4. 石器损坏，需要制作/维护；
5. 原先承诺的公共设施维护项目尚未完成。

**不设一个上帝视角的“部落管理器”自动替所有人决定。** 统一资源事实、时间预算和任务队列，但各居民根据自身已知信息、需求、规范和可行选择决定回应。公共事务通过沟通、承诺与实际执行协调。

两类重要约束：
- **实际可执行**：材料、技能、路径、工时、居住/权限、加载状态、现有任务；
- **社会可接受**：参与者是否知情和愿意、共同使用规则、家庭照料义务、其他人的承诺。

这些是不同的检查，不可以用“优先级数值”混在一起。

## 2. 学术支撑和边界

- Ostrom 的 IAD 框架把参与者、位置、可行行动、信息、控制、成本/收益和实际规则分开描述，适合将“谁有权决定和执行”与“是什么需求”分离。https://www.ostrom.indiana.edu/courses-teaching/teaching-tools/iad-framework/index.html
- Ostrom 1998反对“公共资源一定需要中央命令”的简单假设，指出规则与有限理性行为者的地方自组织。https://dlc.dlib.indiana.edu/dlc/items/e7dbb39b-1d0f-4ccb-bc10-4019b865bfd9
- Tverskoi等（2024，PNAS）建模独立生计劳动与集体劳动在环境冲击下的取舍，发现规范强度与冲击条件互动；是**数学模型的条件性结论**，不是所有史前人类的统一生产规律。https://pubmed.ncbi.nlm.nih.gov/39602270/
- Tanaka（2026）对40名儿童、500余小时观察的跨群体研究强调照料由多种共同作用的关系构成；不应硬编码唯一的儿童照料形式。https://pmc.ncbi.nlm.nih.gov/articles/PMC13476358/
- 我们的任务优先策略属于**游戏化假设**，资源阈值、劳动时段、接受概率应由体验和对照实验校准，不能伪称考古学定律。

## 3. 五层简单机制，不堆“大社会AI”

### 3.1 需求信号 NeedSignal

只保存**确实观察到**的情况：发生者、来源证据事件、时间、地点、受影响成员、严重程度、截止时间、知情范围、是否已解决。允许部分居民不知道问题，事件保留不确定性。

首个可用的 NeedType：`PERSONAL_HUNGER`、`COMMON_FOOD_SHORTAGE`、`CARE_GAP`、`SHELTER_GAP`、`MATERIAL_SHORTAGE`、`FACILITY_REPAIR`。

当前尚无完整真实住房损耗，`FACILITY_REPAIR` 可先用已存在的火塘或工作站损坏、施工中断代替，不能凭空引入灾害。

### 3.2 行动候选 TaskCandidate

每个需求可以生成多种不同任务，例如食物不足可以野外采集、分享请求、玩家贡献、延缓非紧急建设。候选任务必须具备：
- `actor eligibility`：能力、健康、现有角色擅长和权限；
- `material input`：需实际交付、不能重复扣款；
- `time cost`：须占用统一劳动时段；
- `location/path`：目标已知、已加载、可达；
- `expected outcome`：估计收益、风险和副作用；
- `support`：必要的社会同意或委托。

一个任务能够进入行动清单，不等于所有人必须执行它。

### 3.3 居民选择 + 社会协商

- 本人的生存、安全和已承诺照料任务，往往具有很高的紧迫性，但不预设绝对的一刀切价值排序。
- 遵守已有的真实分配规则：例如 `BASIC_NEEDS` 和 `CARE_FIRST_COMMON_STORE`；公共争议仍经现有 `NormSystem`。
- 人格影响风险/互助倾向，但不能取代紧迫程度、材料、技能和路线。
- 允许居民拒绝非紧急建设、提出替代劳动、优先照料孩子，或请求协助。少数贡献者不得自动拥有公共设施的排他所有权。
- 不设每天的全员强制会议；居民只处理确实传到自己的请求和其有权参与的公共事务。

### 3.4 统一时段预留 WorkReservation

必要语义：
```text
FREE -> OFFERED -> COMMITTED -> ACTIVE -> COMPLETED
                        |            |
                        |            -> INTERRUPTED
                        -> CANCELLED / EXPIRED
```

- `OFFERED` 只是意向，不能扣除实际工时。
- `COMMITTED` 是已承诺的时段，预留后其他冲突任务不可重复抢占。
- `ACTIVE` 执行真实村民行为，保持任务持续性，除严重紧急情况/路径错误外不每 tick 重选。
- `COMPLETED` 才提交已核实的劳动成果和材料出入。
- 必须有 `reservationId`、`actorId`、`dayOrInterval`、`taskId`、`sourceNeedId`、`startTime`、`status`、`causeEvents` 与幂等状态迁移。

为现有 `Person` 已有工时扣减与 `VillagerWorkGoal` 实体动作搭桥：新的统一工作时段不应同时与 `careHours/learningHours/socialHours` 再次扣减，需按当时实际代码决定谁是最终真值来源。

### 3.5 营地的 Agenda 仅是共同事务展示，不是统治 AI

`SettlementAgenda` 是由居民当前共同知晓的需求和公开提案生成的**只读视图**，不拥有强制指定全营地工作或越权扣仓的能力。玩家界面最多显示3项当前重大问题，其余可展开，不做数十项“村庄KPI”。

## 4. 优先协调：不要只设一个全村紧迫度总分

### 4.1 先看实际生存边界

当居民严重饥饿或失去照料时，某些必要行动不能被普通工程挤占。这里是**可行性约束**，不是“人人需求完全相等”的制度。

### 4.2 然后看任务依赖和时间紧迫性

例如：
- 工具损坏阻止采集，则修理工具是食物生产的前置工作；
- 建造储藏棚长期有益，但今天的极端缺粮可能要求暂缓工程；
- 日后仍会有同类饥荒，部分居民可能支持投资更好的储藏设施，而不是永远只做当天觅食。

没有永久`priority=100`的工作种类。紧迫度来自可证实需求、期限和风险；社会规则决定谁可以改变公共资源安排；每个居民面对自己的行动成本。

### 4.3 保障+协商结合的初期简化

第一版可先实现**任务优先类别 + 条件性行动**：
1. `CRITICAL`：生存面临近期待处理风险；
2. `COMMITTED`：已经对他人作出而且目前仍可履行的照料/生产/维护承诺；
3. `MAINTENANCE`：维持实际生产设施与工具继续工作的任务；
4. `IMPROVEMENT`：可以推迟、但有未来收益的建设和学习；
5. `OPTIONAL`：不紧迫的交换、装饰或探索。

以上只是**NPC的默认候选分层**，不是社会等级、文明阶段或永久强制法律。允许居民对排序有不同看法。特别是不同家庭可能对相同工程有不同收益。要留出疲劳、休息和非生产性日常生活。

## 5. 最小可玩场景：河谷的三重短缺

一个已加载的8人营地，6名成年人、2名幼儿（都是实验设定，不代表历史人口结构）。现在同时发生：
- 公仓可用食物下降；存在真实采集点但需准备工具。
- 其中一个幼儿当天缺照料支持，照料者因而无法外出。
- 一项公共仓储扩建已有施工进度，但还需要木材、石料和2个劳动时段。

可出现至少三种不同结果：
1. 居民暂缓施工，部分工匠协助恢复食物获取，照料者留在营地；
2. 玩家提供真实食物，缓解当日短缺，使部分居民能保持原工程承诺；
3. 共同体仍选择维护工程，结果短期更紧张，但也可能形成长期储备优势。

**游戏不应预设某一种结局道德上更高尚或总是效率最高。**

玩家看到三个自然语言问题卡片：
- “储粮不够：部分居民正在寻找食物”
- “米雅无法远行：伊洛今天需要照料”
- “储藏棚暂停：缺两段可用劳动和部分原木”

玩家可亲自贡献、请求邻居合作、提出暂缓工程、帮助照料或不干预。其他居民有自己的意愿，前提条件不满足时可以拒绝。

所有物资、劳动与居民关系变动必须具有实际事件和存档后果；不要在GUI里生造一个“本日分配完成”数字。

## 6. Fabric 1.21.1 落地方案

**实现最小范围 P-Coord-01**：只覆盖 `COMMON_FOOD_SHORTAGE`、`SHELTER_GAP`，以及现有建筑项目的暂停/恢复；照料风险只作只读候选来源，等 #28 时段系统落地后再产生可执行照料动作。

实际实现建议：
1. `SettlementNeeds` 和 `SettlementSimulationService` 保留食物事实与真实吃饭；新增轻量**NeedsSnapshot**（只读）按已加载居民观察短缺；不要复制营养库存。
2. `ConstructionPlanner.projects` 继续提出实体建筑候选；增加 `ProjectPriorityPolicy` 或同类纯函数（接受已知需求、已承诺任务和当日材料成本）；“延缓建设”不等于撤销施工 job。
3. `LaborAllocator` 保留专长分工，但 `VillagerWorkGoal` 选择动作前查询居民自身本周期可执行任务，不必全村每 tick 重算名额。
4. 居民当日任务预留可先通过同一 `SettlementSavedData` + 已存在 Person映射实现，时段标识确保一个居民不会同一窗口既施工又外出采集；其后的真正照料和训练继续复用这一预算。
5. 每次行动理由写入诊断快照及事件，`VillagerInteraction` 已能显示实际工作状态；直接在现有 UI 中附上“受什么需求影响而暂缓工作”。
6. 需求汇总/工作承诺只在**规划周期或事件改变**时运算，实体动作只在需要时调整；限制每tick扫描、寻路和消息同步开销。
7. 不使 `SettlementStages` 的标签参与普通工作紧迫性决策。修正其单向阶段的议题应另行评审，以免影响本切片测试。

```java
record NeedSignal(UUID id, UUID settlementId, NeedType type,
                  UUID observerId, long day, Severity severity,
                  List<Long> evidenceEvents) {}

record TaskCandidate(UUID id, UUID needId, TaskKind kind,
                     UUID actorId, int estimatedTime,
                     ResourceRequirements materials, String blockedReason) {}

record ResidentWorkReservation(UUID id, UUID actorId, UUID taskId,
                                long day, Interval interval,
                                ReservationState state) {}

record DecisionTrace(UUID actorId, UUID taskId, List<String> reasons,
                     List<Long> evidenceEvents, String outcome) {}
```

上述仅是**概念字段**。实际开发前必须审阅最新 `SettlementSavedData` 迁移、事件编码与网络同步，不要直接粘贴到 Fabric 项目。

## 7. 实验设计与验收标准

### 正向/对照三组
1. **缺粮 vs 食物充足**：同一营地、同一任务、同一种子，检查应急觅食/建筑的实际工时占比与短缺天数，不能无理由切换。
2. **家庭照料负担低 vs 高**：在将来的可执行照料扩展上线后，检查相同人口与物资条件下可出工时数是否真实改变，不能免费增加工作产出。
3. **社会沟通和承诺不同**：同资源但参与者承诺不同，项目进展及维护是否变化，不能把全营地所有人默认视为支持。

### 必须覆盖的边界与反事实
4. 多个玩家同时给同一居民食物，资源不会重复转移，关系记忆符合真实交付量。
5. 同一 NPC 正在施工时出现急性饥饿，是否安全暂停并保留施工材料、索引和进度。
6. 建筑材料已提交但项目延期，不能双退或双扣；因故取消施工，真实方块不可同时回退成原物品。
7. 存档连续重载两次，`NeedSignal`、`WorkReservation`、进度和事件幂等。
8. NPC 未加载/死亡/迁居时，预留工作不凭空完成；重新加载合理恢复或重新计划。
9. 全部居民拒绝非紧急公共工作时，工程应合理暂停，不会系统强制每个人参加。
10. “阶段标签升为 AGRICULTURAL 但没有火塘”的情形，核对 `ConstructionPlanner` 是否仍能恢复必要火塘，避免历史标签决定当前设施需求。
11. 测试统一工时：长期多个角色和几十个 NPC 不出现每tick大量重复全村名册扫描。
12. 两人联机实机：玩家能用一句话理解某项目为何等待，服务器不因 GUI 决策被客户端越权修改。

**成功标准**：至少出现两条玩家可观察到的分歧路径；两条路径都由材料/劳动/知情/规则差异造成，而非随机剧情触发。真实玩家可在5–15分钟内理解“为什么今天暂停建设”；NPC在没有玩家时仍能自主活动。

## 8. 与跨时代研究的一致性

相同的需求与任务约束机制可复用到 S1灌溉、S2工程贡赋、S3庄园劳役、S5工厂班次及S6公共企业，不同的是谁有权指挥、劳资/照料责任、是否可以拒绝、劳动报酬与生产资料归属。**不能把S0简单命名为“文明等级0”，也不能让现代工厂雇佣制倒灌原始共同体。**
