# S0｜从生活群体到共同体：集体行动、公共工程与实际制度（研究 v0.1）

- 日期：2026-11-04
- 范围：S0，D03劳动、D04资源权利、D05共享、D08治理、D10聚落、D12玩家体验
- 状态：**研究提案，待Agent代码审计和游戏实验**，不等于已经实现的功能，不要求自动新建治理框架。
- 关联：[S0阶段卡](stage-card.md) · [家庭与照料研究 Issue #28](https://github.com/ThySummer14/coopcraft/issues/28) · [玩家参与 Issue #27](https://github.com/ThySummer14/coopcraft/issues/27) · [跨时代框架](../../framework/cross-era-master-v0.1.md)
- 工程：CoopCraft / Minecraft Java 1.21.1 / Fabric / Java 21；依赖现有 `civilization.simulation`、真实库存映射、`SettlementSavedData`、`ConstructionPlanner` 与 `ConstructionSystem`，具体类/接口以最新源码为准。

## 1. 研究核心问题

**没有国家或统一行政机构的多个生活群体，怎样围绕真实物质需求组织劳动，形成公共设施，并在使用、维护和冲突中产生社会规则？**

重点不是给“部落首领”加命令菜单，而是让居民因实际需求形成临时协作、条件性承诺、自愿参与、委托协调及规则争议。项目是社会关系的载体，而不仅是建筑蓝图。

## 2. 研究证据与边界

1. **公共建筑与劳动规模**：Jerf el Ahmar、WF16等早期新石器遗址存在大型、可能具有多种共同体用途的建筑。它们支持复杂共同施工与设施使用的可能性，但**不能直接证明投票、全员平等、首领强迫或统一所有权**。Finlayson et al. 2011, *PNAS*: https://pmc.ncbi.nlm.nih.gov/articles/PMC3100919/ ；Kodas, Jerf el Ahmar: https://books.openedition.org/psorbonne/4630
2. **合作依赖社会情境**：Hadza 四年合作实验追踪56个营地、383人，当前营地同伴合作行为对个人行为有较强关联；不支持仅凭一个固定“无私/自私”性格决定合作。Smith et al. 2018, *Current Biology*: https://pubmed.ncbi.nlm.nih.gov/30245106/
3. **制度多样性**：四个非洲采集狩猎群体的跨文化研究记录了决策和限制过强权威的多种方式，不应把所有无国家社会做成一套开会投票程序。Thomson et al. 2025: https://journals.sagepub.com/doi/full/10.1177/10693971251338210
4. **地方共管规则**：Ostrom 的边界、成本与收益协调、受影响者参与、监督、冲突解决等是检查治理系统的分析工具，不是声称史前社会都逐项遵守的历史事实。Anderies et al. 2004: https://ecologyandsociety.org/vol9/iss1/art18/inline.html
5. **跨文化差异**：Henrich et al. 2005 小规模社会经济实验显示合作动机和社会规则与具体社会背景关联，不能把居民简化为统一的理性自利选择器。https://pubmed.ncbi.nlm.nih.gov/16372952/

## 3. 核心概念：先分清项目、资源和权利

- **共同建设项目（Project）**：需要多人或跨家庭投入的实际任务；例如修葺公共仓的遮雨棚、修复火塘、维护公共作业区。
- **工作队（WorkParty）**：某一时段实际协作的成员集合；成立不等于永久职业或部落。
- **贡献/承诺（Contribution/Pledge）**：具体可交付的物资、劳动时段、场地或知识支持。**承诺不是已经付款**。
- **公共设施（Facility）**：建造后具有实际用途、损耗、维护和物理位置的世界对象。
- **资源使用权（RightsInUse）**：谁能使用、管理、收益、排除他人、制定规则；这些权利不自动根据出资比例确定。
- **治理安排（Rule/Coordination Arrangement）**：实际行为如何被协调以及如何解决冲突，可能无会议/无首领。
- “公共产品”“公地资源”“共同持有财产”不是同义词。建筑本身的共同投资、储藏空间的分配以及渔场的资源提取，需要不同的权利与稀缺性规则。

## 4. 居民为何参与：决策依赖场景

```text
看见需求(自己已知的仓储不足/设施破损)
 → 是否有能力付出？(材料、工时、照料、工具、路线)
 → 方案预期价值？(自己/家庭/朋友/营地将如何受益)
 → 期待他人是否真的参与？是否有人承担协调？
 → 现有规则/承诺/公平观念与信任
 → 加入、部分加入、条件性加入、提出替代方案、拒绝
```

所有人保有知情边界与实际行动自主权。不能“村庄只要人数>8就自动集体修房”。人格影响倾向，但不决定单次行为；缺粮家庭拒绝参加并不意味着“搭便车”，因为其家庭可能承担照料和其他劳动。

**条件性承诺**：如甲承诺提供石料，条件是乙能出运输劳动；只有满足条件才允许占用实际可支配资源和工时。承诺应可到期、撤回并产生不同后果。

## 5. 一个完整的可玩纵向切片：修缮公仓遮雨棚

已有公共仓库所在位置连续受到雨水影响，部分物资面临损坏风险。玩家可以不参与。

1. **产生项目需求**：仓库实际容量、建造状态、环境或临近短缺触发项目候选，不预设剧情倒计时。
2. **提出方案**：知情的居民提出“修缮遮雨棚”；说明材料、地点、劳动时段、实际受益对象、建成后的维护者候选。
3. **招募与协商**：居民面对面的接触或通过已知关系得知提案；可以愿意出物资但不出劳力，可以同意修建但争论使用权。
4. **实际承诺**：承诺的材料和劳动力做登记，并核查是否真实可用；可保留两个等价路径（共同承诺材料/玩家直接完成部分修建），避免强制召开议会。
5. **正式实施**：工作队协作，消耗材料、工时并逐块施工，玩家可共同加入；无人参与则项目停滞。
6. **使用与维护**：登记设施后，只按认可的实际规则使用，记录维护任务与损耗。
7. **反馈和冲突**：围绕“谁负责维护、谁优先使用、参与者与未参与者如何使用”产生合理争议；可能协商、改规则或保持旧安排。

此处的“遮雨损坏”属于可选游戏化假设；若现有原版箱子/物品暂无腐坏，MVP可只针对**容量缺口与仓库扩建**，不要凭空宣称已实现自然灾害机制。

## 6. 建议的状态机（与现有施工进度分开但关联）

```text
DRAFT (提出)
  -> OPEN (招募/提出条件)
  -> READY (场地合法，必要物资与最低可行工作队)
  -> EXECUTING (真实施工，事件账本)
  -> OPERATING (设施可用并附带规则/责任)
  -> MAINTENANCE (使用中需要维护)
  -> OPERATING / RETIRED / ABANDONED

DRAFT/OPEN/READY/EXECUTING 也可进入
  -> BLOCKED (缺材料、工时、路径或权利，明确原因)
  -> CANCELLED (撤回或失去可行性，处理已保留的物资)
```

未完成/中断不得凭空删除或生成材料；若材料已消耗变成真实方块，不可在取消时同时退款。状态迁移必须幂等，旧存档默认不拥有虚构的项目/承诺。

## 7. 可复用对象（概念伪结构）

```java
CollectiveProject {

  UUID proposerId;

  LaborCost laborCost;

  String blockReason;

ContributionPledge {
  UUID actorId;
  UUID projectId;
  ContributionType kind; // MATERIAL | LABOR | TRANSPORT | SITE
  ResourceRequirement quantityOrTime;
  Condition optionalCondition;
  boolean fulfilled;

ProjectWorkEvent {
  UUID projectId;
  UUID workerId;
  TaskType workType;
  long timeSpent;
  List<Long> materialTransferEventIds;

```

**只定义相容于现有对象的字段增量**，不要照此复制完整平行经济账本。尤其要确保材质库存单一权威：项目“承诺”、库存“预留”、实际“转移/消耗”是三种不同状态，须保证绝不双扣、双出。

## 8. Minecraft交互（避免现代议会UI）

- 用现有钟/火塘作为查看公共事务的入口；右键具体居民了解“正在参与什么工程、为什么、缺什么”。
- 公共事务卡片最多展示“是什么事、为何需要、还缺哪些材料/工作、有哪些争议、玩家可做什么”。
- 玩家可贡献真实材料、请求加入一次施工、提出替代地点、表达方案意见；**不能远程强制所有村民出工或把所有公仓变为私产**。
- NPC 可拒绝、迟到、改变承诺，也可在玩家不在场时独立推进。
- 不要每个 tick 进行社会议事；每日或事件驱动规划，具体Minecraft工作按 tick预算执行。
- 旧工程中的 `ConstructionPlanner` 和 `ConstructionSystem` 负责选址/实际方块，Project 仅扩展需求、协作与权限，不重写蓝图施工。

## 9. 正向对照实验

A. **同等物资、不同关系网络**：在全部材料充足但居民互信关系不同时，项目成立率、招募耗时和履约是否不同？不要硬编码结果。
B. **同等关系、不同家庭照料负担**：某家缺劳力但能提供木材；多人协作是否允许替代贡献并记录照料劳动？
C. **相同建成建筑、不同管理规则**：共同管理、特定家庭委托管理、轮流管理分别怎样影响使用与维护？注意控制资源条件。

## 10. 失败、反事实与兼容实验

1. 仅一人承诺全部工程但缺少实际材料：项目不能启动，也不因点击UI凭空完成。
2. 同一村民被安排照料孩子和同时采石施工：不应重复结算劳动时间。
3. 分支存档两次重载：承诺、材料预留和实际施工进度均只结算一次。
4. 参与者迁移、死亡、失去路径或卸载：项目合理暂停/重新招募，无远程实体瞬移。
5. 玩家重复提交、多人联机竞态、仓库已满：服务端验证并保持物资守恒。
6. 建筑已完成后发生争议：不得直接把实体建筑消失或材料退回；仅改变权限/使用/维护安排。

## 11. S0范围和下一步交接

**首个实现建议**：只做一种公共设施（现有公共仓的简单扩建/修缮），一项项目对象，一种可以拒绝的参与邀请，一条玩家贡献材料或劳动的入口，真实完成/失败/恢复和事件追溯。优先作为独立模拟可复现实验，通过后再接入一个真实Fabric GameTest。

**暂缓**：正式税制、强制劳役、行政部门、所有居民实时投票、复杂惩罚、永久政党、土地全面划界、跨营地大型工程及向后续社会阶段强制升级。

**与后续阶段的关系**：同一项目和劳动承诺接口可复用于S1灌溉与耕作、S2大型公共工程、S3庄园劳役、S5工厂建设及S6公共企业。变化的是谁有提出/指挥权、是否自愿、劳动回报和剩余归属，而非重写一份施工系统。
