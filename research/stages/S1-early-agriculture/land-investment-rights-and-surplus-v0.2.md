> **本轮必须回答**：同一块地被长期耕作、维护与储藏后，为什么可能产生持续的占有和收益主张？不同行动者如何认可、拒绝或修订？在 Minecraft 中，怎样既能玩又不变成禁止破坏方块的领地插件？

## 0. 六条实施决议（ADR-S1-001 至 ADR-S1-006）

1. **地块是现实空间对象**，长期投入应首先留下实际方块、路线、设施及已花费的劳动事件。第一版**不引入魔法肥力/固定+X%产量**；改善生产仅通过现有的含水、真实障碍、路程、围护及可操作方块产生影响。
2. **承认的使用权不等于拥有土地**。保留进入、耕种、收获、管理、安排分配、限制他人使用等可拆权能；批准项目/实际出工/担任协调者不自动转成永久排他所有权。
3. **收获物的物理保管权、被认可的领取主张和受益权分离**。第一版所有受托实体物品可存入真实公仓，并通过有来源的领取授权进行分配；不可在数据库给家庭写一份作物，又在公仓保留另一份。
4. **真实家户容器是独立开发任务**。`StorageOwner.household` 已存在于纯Java核心，但 `MinecraftStockpileAdapter.validateCamp` 目前只允许营地保管者。未经适配器改造不得在 UI 宣称“已放进家庭箱子”。S1-P1先实现家庭领取权，S1-P2再做真实家庭储藏绑定和一次性搬运。
5. **社会规则不硬塞进现有`Norm.allocationUnitCap`**。保留旧公仓配给规则；土地规则采用独立的轻量`PlotRule`状态和行动评估，经过现有信息传播/社会提案/事件回放机制形成和修订。通用提案基础设施如需抽象，应独立重构并保持老存档兼容。
6. **不把农业、积累、财产差异自动解释成阶级或国家形成**。土地生产能力、家庭可食物量、对工具/地块的使用权、对他人劳动的实际命令权及代际延续分开观察。技术/制度允许反转。

## 2. 地块长期投入的四种游戏情形（P1先做前两种）

| 投入 | 真实Minecraft行为 | 真实成本 | 对农业的客观影响 | 社会权利问题 |
|---|---|---|---|---|
| 开垦 | 移除杂草、清理遮挡、改变表层土方为耕地 | 实际时间、工具耐久、可能材料 | 田块变得可种 | 先开垦者是否取得下一轮优先使用？ |
| 引水/靠近水源 | 使用真实水源和现有耕地含水机制 | 路线、材料、真实方块改造 | 改变 FARMLAND 实际湿润条件 | 谁维护公共供水、谁优先使用？ |
| 围护 | 实际栅栏、围墙、门等建筑 | 原木、工具、建筑工时 | 可能减少部分踩踏/进入，但不能假设全防护 | 物理限制是否得到其他成员认可？ |
| 道路/储藏 | 真实通路、桥、仓、工作站 | 石木、施工时间、空间 | 运输与加工更方便，有实际可达性影响 | 谁能使用、谁负责维护？ |

**P1第一轮限制**：只实现“开垦后登记劳动来源”与“有/无真实水源的耕地性能差异”；围护与道路可沿用已有建筑系统，在第二轮扩展。完全不新增独立肥力字段；若今后做肥料/休耕，必须具有真实投入、消耗、作用和失效规则，还要避免双份随机tick作物生长。

### 2.1 投入记录不等于永久地权

`LandImprovement` 是`InvestmentEvent`，记录`actorId, plotId, actualBlockChanges, materialBatchIds, laborReservationId, eventId`。  
`LandUseClaim` 是某人或生活小组提出的一项社会主张，记录`claimant, plotId, rights, claimedReason, evidenceEventIds, acknowledgedBy, status`。

**不得设定**：耕10次/种100次→永久自动私有。系统可以因为连续使用与改良形成一种高“认可倾向”，但只在其他成员实际知情、同意/默认接受并可被提出异议时转成可执行规则。

## 3. 最少五个社会性权利（不引入现代土地买卖）

| 代码权能 | 对应操作 | 与其他权能区别 |
|---|---|---|
| `ACCESS` | 进入耕地附近、经过田间通道 | 进入不等于有收获权 |
| `CULTIVATE` | 翻土、播种、照料 | 耕种不等于全部收获归自己 |
| `HARVEST` | 实际收割指定作物 | 取得物品不等于独占全部成品 |
| `MANAGE` | 决定什么时候播种、管理轮换/修建田边设施 | 管理者可以是可撤换的协调者 |
| `ALLOCATE` | 依据社会认可安排收获后产品的保管与领取 | 不是任意转移私人所有物的上帝权限 |
| `EXCLUDE` （P2） | 对谁可以进入/使用作出限制性主张 | 首版只做社会性异议与配置化保护，不强制锁定方块 |

暂缓`ALIENATE` 土地买卖、抵押，及复杂永久世袭地权；这些属于S3/S4等其他研究单元的重点。身份和物品持有关系不得由`SettlementStage.AGRICULTURAL`自动填写。

### 3.1 起始政策三种（同一代码路径的参数集）

- `HOUSEHOLD_STEWARDSHIP`：某生活群体优先安排播种/收获；其收获领取权由协议定义；公共储备可以继续存在，其他人可能求助。
- `COMMON_FIELD`：多人共同劳动和安排产物使用，管理规则经过参与者形成；种粮并不必然所有人贡献相同工时。
- `ROTATIONAL_USE`（P2）：若干家庭依约定轮次安排农地使用；轮次变更不生成新地产，也不清除历史投入。

这些是**游戏里允许的制度配置**，不是一个历史时期必须满足的三种社会分类。社会规则的正当性由居民关系与实际协商实践体现，不是文件里设置`policy=COMMON`就让所有人立即服从。

### 3.2 建议的数据模型

`FarmPlot`（延续既有S1文档）：`plotId, settlementId, dimensionId, positions, cropKind, actualStateRef`，不保存独立生产库存。`actualStateRef`必须是 Minecraft 方块读数，而非一份后台作物年龄。

`PlotRule`：
`ruleId, plotId, policyType, grants[] {actorOrGroupId, rightsSet, startsDay, endsDay}, sourceProposalId, activeRevisionId, notifiedActorIds, dissentActorIds`。序列化到`SettlementSavedData`的新版本字段，旧版缺省时采用“未分配权利/不推断家族所有权”，不能凭房屋邻近关系自动分配。

`PlotClaimEvent`：
`claimId, proposerId, rightRequested, supportingInvestmentEventIds, proposedDuration, endorsements, objections, status`。
多数票不必是所有规则的通用机制。接受基于实际成员知情、合法身份、家庭与公共利益和地方惯例；不知情者不要立即自动支持。

`CropReceipt / HarvestClaim`：
`harvestEventId, plotId, actorId, actualHarvestItems, physicalStorageOwner, authorizedRecipientId, claimQuantity, allocationRuleId, status`。
**收获收入库和居民有权领取是两种事实**。只有从真实公仓/批次成功分配出去，才能扣减少相应的物理总量与未履行领取权。未卖出、未领取和已消费不同。

`Reservation`：
`reservationId, batchId/itemLocation, purpose {SOWING, COMMUNITY_NEED, CLAIM_REDEMPTION}, amount, claimant, expiryDay, state`。
种子“预留”只是对现有真实库存的一项不能重复占用的约束；不得创造另一份种子余额。

## 4. 四段式实物账本：防止经济系统产生隐形资源

`WORLD_BLOCK` 真实成熟植株 → 玩家/NPC一次权威收割 → `GROUND_DROPS`（如果真实掉在地上） → `PERSON_INVENTORY` → `CAMP_CHEST_OR_ABSTRACT_CAMP_OWNER` → 授权实际分发→ `PERSON_INVENTORY / CONSUMED`。

- **没有实际入包的地上掉落不计入已储备粮食**。
- 可记录“应得份额”，但不得把应得份额当成已经交到手的物品。
- 权利争议只暂停分配或记录未经认可的领取，不能凭空撤销已经完成的方块收获。
- 旧版`MinecraftStockpileAdapter` 仅明确支持`StorageOwner.camp`。若要家庭实体仓：必须新适配`StorageOwner.household`与真实箱子UUID/坐标绑定、装卸与重载验证之后才能启用。
- 当前`ResourceType.TUBERS` 可与`Items.POTATO`对应；但首版不自动把模组所有马铃薯视为“农田出产”，生产来源必须从`CROP_HARVEST`记录，旧`GATHER`与耕作分开。

### 4.1 用真实库存作分配示例

在`EXP-S1-010`的固定测试场景中，一次完成的收获**实际得到20个马铃薯**。小组已经确认下轮播种需要8个，并有公共照料请求。

| 实际分配目的 | 数量 | 状态 |
|---|---:|---|
| 下轮播种预留 | 8 | 原物品仍在营地仓库，只有用途预留 |
| 公共照料口粮 | 4 | 按现行公仓规范成功领取才算实际消费 |
| 耕作家庭可领取份额 | 8 | 先是经认可的领取主张，履行后才转入实际背包 |
| **总数** | **20** | 任何时刻一份物品只能有一个权威保管位置 |

**说明**：20是实际拾取后的测试夹具数量，不是“播8颗必得20”的隐藏收益率；8/4/8只是用于验收分配协议的虚构比例，任何收获少于20时要按短缺政策真实调整。

## 5. 可执行的居民决策，不生成全村统一意志

**行动候选**：`FORAGE`、`TILL`、`SOW`、`TEND`、`HARVEST`、`TRANSPORT`、`PROCESS_FOOD`、`CARE`、`BUILD`、`REST`。

**五项硬约束**：
1. 居民实际拥有且当日可执行的劳动时段，不能与已经承诺的照料/建筑冲突；
2. 目标地块和作物在已加载范围内可验证，存在可达路线；
3. 实际库存中存在未被其他工单预留的种植材料；
4. 社会规则与当事人已知信息允许申请/行动；若违反，可照常发生物理动作但应有真实后果；
5. 真正准备收获时检查成熟`BlockState`和相应`mobGriefing`/原版 Farmer AI兼容。

**偏好排序只是可配置的游戏假设**：比较短期生存、预计未来粮食、工作成本、已作出的承诺、共享规则、家庭需要、技能与风险。一个居民不能读取全图最佳农田或未告诉他的远处仓库。

### 5.1 不让私人投入变成自动的政治升级

居民提出“上次我开垦了这块地，希望下轮继续种”，其他居民可能有四种回应：
- 认可优先使用，但产品仍按共享规则分配；
- 认可某种补偿性的收获领取权；
- 不认可长期排他，因为公共开垦和其他家庭劳动参与过；
- 暂时无法决定，依旧合作耕种并保留争议。

这些回应须由实际关系和知情传播形成。**禁止写死“连续三轮耕种，自动成为地主”**。

## 6. 真实 Minecraft 玩家互动设计（只用2个入口）

### 入口 A：潜行右键登记耕地边界/田间工作点

`田地：河边小田 / 当前状态：已播种8格、成熟3格 / 管理安排：米雅家庭负责播种，其他家庭可参与收获 / 储藏：公共仓保管 / 本轮维护：水源附近需清理1格`。

玩家可执行：
- 查看实际作物/物资与来源；
- 请求协作播种/收获（NPC可以拒绝）；
- 贡献真实材料/种子；
- 提出下一轮轮用/共同耕作的改议；
- 无视规则直接操作Minecraft方块（默认不硬锁），事后由参与者观察并可能产生`PROPERTY_DISPUTE`事件。

不是新增一个全图“田产管理台账”大界面。农田注册初版可以为简单的两点选区或既有钟/名册里加入`登记附近耕地`，由服务端严格检查范围最多16格/同维度/不跨重叠管理域。

### 入口 B：既有村民右键/公共仓

点击居民显示`正在做什么｜为什么｜缺少什么｜谁可以使用当前作物`。公仓显示**真实数量、已经预留的种子、尚未履行的领取主张**，不能把相同份额同时计入各家的实物持有量。

玩家作为访客提出建议不自动改变共有规则；玩家可以自己劳动，居民根据约定接纳/反对其主张，决策有持久来源。

## 7. 最小工程架构与不可破坏的旧系统

| 系统 | 新职责 | 保留的权威 |
|---|---|---|
| `SettlementSavedData` | 版本化保存地块ID、规则ID、已执行事件、授权/预留；缺省旧档不推产权 | 继续保留已知稳定居民UUID |
| `VillagerWorkGoal` | 工作候选中增加农田`SOW/HARVEST`和明确原因 | 实体寻路/行动只有一条执行路径 |
| `LaborAllocator` | 保留身份/技能偏好，可临时改做采集或照料 | 不给“农民职业”永久排他 |
| `MinecraftStockpileAdapter` | 保留营地唯一权威；先用马铃薯验证事务和来源 | 不能未实现家庭容器就假装“家庭有粮” |
| `simulation.SimulationWorld` + `StorageOwner` | 记录批次、来源、家庭主张和公共分配事件 | 不重复收获产生第二批次 |
| `NormSystem` | 复用社会知情、协商和监督经验；土地权利使用结构化规则服务 | `Norm`现有`allocationUnitCap`仍只服务现有口粮约定 |
| `ConstructionSystem` | 限定的真实土地清理、水源整理、围栏/通路项目 | 原有材料扣除与真实方块进度 |
| `SettlementStages` | 只做展示/历史里程碑，不驱动权利赋值 | 阶段状态单向晋级问题独立开发评审 |
| `tools/probe` & YAML卡 | 可重复检视三种分配与权利分歧 | dev-only，不进入发行模组 |

**硬性顺序**：农田真实生产（S1-P0）稳定后→形成领取权/土地规则（S1-P1），再建家庭真实容器（S1-P2）；若顺序倒置，很容易做出一套只在面板里存在的虚拟农业。

## 8. 正反例实验矩阵（固定种子、同样真实世界初态）

| ID | 单独变化 | 必须观察 |
|---|---|---|
| `EXP-S1-010` | 同一收获的`HOUSEHOLD_STEWARDSHIP` vs `COMMON_FIELD` | 方块产物不凭空变多，真实领取对象/可用种子因规则而不同 |
| `EXP-S1-011` | 开垦居民能否获得下一轮优先耕种的社会认可 | 认可、拒绝或提出期限条件的过程与被知情人相关 |
| `EXP-S1-012` | 同样地块有/无真实水源 | 原版湿润状态/实际成熟速率可能不同，不造另一个作物时钟 |
| `EXP-S1-013` | 长期投入较多 vs 少；给其他条件一致 | 实际劳时、设施可用性、投入回报、争议和预期变化 |
| `EXP-S1-014` | 公仓短缺但有种子预留 vs 无种子预留 | 当前饥饿与下一轮真实播种能力形成不同结果 |
| `EXP-S1-015` | 耕作家庭迁离，留存真实方块与历史事件 | 权利可过期/转委托，地块和粮食不能被删除或复制 |
| `EXP-S1-016` | 耕作与照料时段冲突 vs 不冲突 | 无人同一时段“双倍生产”，且可提出替代协作 |
| `EXP-S1-017` | 玩家参与/不参与；相同物资与随机种子 | 玩家实际劳动/捐种改变后续行动，而非任务脚本强制完成 |
| `EXP-S1-018` | 两个NPC与原版Farmer争夺同一成熟作物 | 一次合法BlockState改变、一次Loot生成、一次入账，不重复收获 |
| `EXP-S1-019` | 连续两次存档重载/玩家断线/库存满 | 收获、授权、预留、物资和修缮进度幂等 |

**检验分化，禁止预设必然方向**：分别跟踪(1)家庭实际可领口粮天数；(2)每户可使用地块/工具份额；(3)居民真正完成的劳动与照料时间；(4)未履行的领取主张和争议；(5)对其他人劳动的实际指挥/控制；(6)换代后哪些规则仍被承认。只有观察到持久差异与控制关系，才可以分析分化，不通过“积累100谷物自动出现贵族”。

### 8.1 游戏可玩性的量化验收（数值是开发标准不是历史数据）

- 在预置成熟作物的`EXP-S1-010`中，玩家能在**5分钟**内发现当前土地使用安排与至少一种可执行帮助；
- 预置一次有争议的收获时，玩家能通过**不超过两次交互**读懂“谁劳动、粮食存哪里、谁有权领取”；
- 至少两个不同社会安排产生不同真实分配/工作结果，但每轮实际收获物品总数保持来源一致；
- 原版未登记农田的原版村民行为与`mobGriefing`设置不退化；
- JUnit长期种子、Fabric GameTest、两人联机、NBT两次重载及主线程/网络性能回归都具备可复现结果；
- 若无玩家，营地仍可独立规划播种、继续S0采集或因短缺放弃农活，不能成为“只能玩家点田才能发展”的系统。

## 10. 研究收束决定与跨时代复用

S1本专题研究已提供：土地真实投入、权利束、双层保管/请求、事件/规则形成、非必然社会分化、具体Fabric接入、10组可复现实验和四个分阶段PR。接下来应靠代码与实验发现新问题，而不是继续发明第三套社会关系抽象。

向S2只扩展机构征集与劳动强制的来源及治理成本；向S3深入地租、多层土地权利与继承；向S4/S5引入真正价格/契约/工资/融资与资本增殖。**同一个`PlotRule`和`CropReceipt`可在不同制度下重用，价值在于变更权利与劳动关系，而不是更换整个Minecraft农耕引擎。**

**保留不确定性**：农作和财产权协同发展是重要的理论解释，不是全人类史唯一解释。实际Minecraft游戏会优先保障多路径的可玩性和因果透明度。
